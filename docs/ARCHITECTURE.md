# Архитектура

## Поток данных

```
InputSource ──> Player / HUD
                   │
                   ├─> DamageResolver ──> HealthComponent / GameState
                   │                          │
                   │                          └─> EventBus (сигналы)
                   │                                   │
                   ├─> Telemetry <─────────────────────┤
                   │           │                       │
                   │           └─> user://debug_runs/<run_id>/
                   │                                   │
                   └─> AudioManager <──────────────────┘
                               └─> user://settings/audio.json
```

`EventBus` — единственный канал оповещения. Никто не держит прямых ссылок на
HUD, кроме сцены `main.tscn`. `AudioManager` тоже подписан только на сигналы
(см. «Звук»), поэтому удаление аудиоautoload'а глушит игру, но не меняет ни
одной механики.

## Autoload

| Имя | Файл | Ответственность |
| --- | --- | --- |
| `Telemetry` | `scripts/core/telemetry.gd` | Логи прогона, перехват ошибок движка |
| `EventBus` | `scripts/core/event_bus.gd` | Сигналы между системами |
| `GameState` | `scripts/core/game_state.gd` | HP/мана/XP/золото/инвентарь/флаги |
| `QuestManager` | `scripts/quests/quest_manager.gd` | Состояния квестов, цели убийств и сбора, выдача награды |
| `SaveManager` | `scripts/save/save_manager.gd` | Слоты, атомарная запись, миграции |
| `InputBindings` | `scripts/core/input_bindings.gd` | Переназначение клавиш, `user://settings/controls.json` |
| `HitStop` | `scripts/core/hit_stop.gd` | Общее замедление времени после удара, всегда возвращает `time_scale` к 1.0 |
| `AudioManager` | `scripts/core/audio_manager.gd` | Шины, пул плееров, громкости, `user://settings/audio.json` |
| `Accessibility` | `scripts/core/accessibility.gd` | Вспышки, размер шрифта, дальтонизм, `user://settings/accessibility.json` |

Autoload'ов ровно девять: всё остальное — сцены и компоненты.

## Ввод

`InputSource` (`scripts/core/input_source.gd`) — статический фасад. Человек
читает `Input`, бот подменяет источник через `InputSource.set_override()`.
И игрок, и HUD опрашивают только `InputSource`, поэтому у бота нет
привилегированного доступа: он не может вызвать `queue_free` у врага или
прочитать его HP.

HUD не читает однокадровый `just_pressed` напрямую: `_input` фиксирует нажатие
каждого опрашиваемого действия в защёлку (`_pending_input`), а `_process` её
потребляет, — так нажатие не теряется, если пресс и релиз попали в один кадр
`_process` (длинный кадр, загрузка CPU); при активном оверрайде бота `_consume_action`
читает `InputSource` напрямую, и поведение бота не меняется.

Экран «Настройки» (`scripts/ui/settings_panel.gd`, открывается из паузы) — три
секции на одном экране: переназначение клавиш, три громкости (Музыка, Звуки,
Интерфейс) и «Экран» (яркость вспышек, размер шрифта, дальтонизм). `Tab` переводит
курсор между секциями по кругу (Управление → Звук → Экран → Управление), а заголовки
служат переключателем, поэтому всегда видно, какой секции сейчас принадлежат стрелки.
Секция управления читает сырые `InputEvent` — иначе перехватить произвольную
клавишу нельзя. Бот сырые события не порождает, поэтому ни переназначение, ни
громкость, ни настройки экрана для него недостижимы, а правки `InputMap` на его
прогоны не влияют. Назначения пишет `InputBindings` в `user://settings/controls.json`,
громкости — `AudioManager` в `user://settings/audio.json`, настройки экрана —
`Accessibility` в `user://settings/accessibility.json`; все три отдельно от слотов
сохранения (ТЗ §18). Значения меняются шагами по 10 (`←→`), сброс выбранного — `R`,
выход и запись — `Esc`. Значения «Экрана» живут в одном месте — autoload'е
`Accessibility`, — а панель читает и пишет их по ключу, поэтому второй копии,
способной разойтись с тем, что реально применяют HUD и вспышки, у панели нет.

Экран «Персонаж» (`scripts/ui/character_panel.gd`, открывается на C) — панель
характеристик, производных чисел и невложенных очков; опрашивает `InputSource`
через HUD, как остальные панели, и тратит очки только через
`GameState.spend_attribute_point()`.

Экран «Навыки» (`scripts/ui/skills_panel.gd`, открывается на K) — один
плоский список всех восьми навыков, сгруппированный заголовками школ, а не
четыре школы по `Tab`: при 480×270 вкладки прячут шесть навыков из восьми,
а плоский список показывает все строки с ценой, кулдауном и статусом
(выбран / изучен / закрыт) сразу; курсор один, как в инвентаре, лавке и
листе персонажа. `E` делает строку активным навыком через
`GameState.select_skill()` — именно он затем летит с ПКМ; `L` изучает
закрытый навык за очко навыков через `GameState.learn_skill()`, которая
списывает очко только при успехе. Очки приходят по одному за уровень
(`skill_points_per_level` в `data/progression.json`) и хранятся в
`GameState.skill_points` вместе с сохранением. Строка маны в HUD обновляется
по уже существующему `EventBus.skill_selected` — нового сигнала не заводили.

## Бой

`DamageResolver.resolve_hit(attacker, target, payload)`:

1. отбрасывает повторный `hit_id` для той же цели;
2. считает крит, вычитает `get_defense()` цели;
3. вызывает `receive_damage()` у цели;
4. пишет событие в `combat.jsonl`.

Удар игрока: `WINDUP 0.08 → ACTIVE 0.10 → RECOVERY 0.16`. Хитбокс открывается
только в ACTIVE, `hit_id` создаётся один раз на замах.

### Комбо

Цепочка ударов (ТЗ §6 «Комбо зависят от оружия») живёт на `Player`, а все её
параметры берутся из данных надетого оружия — `ItemDB.combo_steps()` и
`ItemDB.combo_window()`. Шаг цепочки: `damage_mult`, `windup`, `active`,
`recovery`, `reach` (множитель выноса хитбокса) и `arc` (множитель его размера).
`iron_sword` — 3 быстрых шага, `iron_spear` — 2 медленных, но с бо́льшим
вылетом.

Новое оружие кода не требует: достаточно положить `combo` в `data/items.json`.
Оружия без `combo` (и кулаки) бьют одиночным замахом из констант `Player`,
поэтому ничего не регрессирует.

Порядок такой: шаг выбирается в момент старта замаха, а после его окончания
открывается окно комбо (`combo_window` секунд). Следующая атака внутри окна
переводит цепочку на следующий шаг, после последнего шага — по кругу на первый.
Окно протекло — цепочка обнуляется, и следующий удар снова первый шаг. Окно
тикает только вне замаха: у копья шаг (0.66 с) дольше собственного окна (0.55 с),
и иначе цепочка обрывалась бы под ударом, который ещё идёт.

### Статусы

`StatusComponent` (`scripts/combat/status_component.gd`) — переиспользуемый узел
эффектов (ТЗ §8.2). Навешивается кодом на `Enemy` и `Player` (не через `.tscn`).
Шесть статусов: `burn` (горение, периодический урон), `chill` (холод, замедление
до 0.6), `shock` (разряд, блокирует действия), `root` (корни, блокирует
движение), `blight` (порча, периодический урон и лечение ×0.5), `stun`
(оглушение, блокирует действия и движение).

Любое будущее заклинание получает статусы бесплатно: достаточно положить в
payload `DamageResolver.resolve_hit` ключи `status` и `status_duration` —
резолвер вызовет `apply_status()` у дочернего `StatusComponent` цели.
Сопротивление цель отдаёт через метод `get_status_resistance(status)` (0..1);
полное сопротивление (1.0) отклоняет статус. `burn`/`blight`/`chill`/`root`
складываются (до 5 стаков) и обновляются до большей длительности; `shock`/`stun`
не стакаются, только обновляют длительность. Периодический урон (`burn` 3,
`blight` 2 за тик, умноженно на стаки) идёт обратно через `DamageResolver`, а не
напрямую, поэтому подчиняется тем же правилам дедупликации, защиты и телеметрии.

## Комбинации

`Combinations` (`scripts/combat/combinations.gd`) — единственная таблица
элементальных взаимодействий (ТЗ §9.2). Правил четыре:

| Комбинация | Что происходит |
| --- | --- |
| лёд + физика | по замороженной цели физический удар выбивает более глубокий стаггер (+0.25 с); урон не меняется |
| огонь + корни | корни сгорают, остаётся маркер дыма (`SmokeZone`, 3 с); урона нет никакого |
| молния + мокрая цель | `shock` по цели с `chill` бьёт по ближайшим врагам в 70 px, не больше `MAX_CHAIN_TARGETS` (3), уроком вдвое меньше исходного |
| лечение + порча | лечение сгорает по одному стеку `blight` и проходит с множителем 0.5 |

Единая точка входа: `DamageResolver.resolve_hit` вызывает
`Combinations.on_hit()` до передачи результата в `receive_damage()` (иначе цель
не успеет прочитать блок `combination`) и `Combinations.on_status_applied()`
сразу после успешного `apply_status()`. Лечение идёт через
`Player.heal_with_status` → `Combinations.on_heal()`. Ни один атакующий, ни один
статус, ни один навык своего правило не реализует.

Защита от рекурсии: цепная молния резолвится с флагом `no_chain: true` и без
ключа `status`, поэтому второй уровень не возникает даже теоретически;
дополнительно счётчик `_chain_depth` и потолок `MAX_SMOKE_ZONES` держат под
контролём и глубину, и число маркеров. `on_hit()` не наносит урона вообще, так
что ни одно правило не может породить новый `resolve_hit` из `receive_damage()`.
Мёртвая цель не реагирует ни на одно правило, а удар, оказавшийся смертельным,
теряет блок `combination`.

## Враги

`Enemy` (`scripts/ai/enemy.gd`) — явная FSM с таймером состояния. Телеграф —
`ColorRect`, который проявляется во время WINDUP; хитбокс открывается после.
Дальний враг стреляет снарядом (`Projectile`), урон всё равно идёт через
`DamageResolver`. Отличия конкретного типа задаются не новым скриптом, а
экспортами `Enemy` — `speed_multiplier`, `attack_cooldown_multiplier`,
`windup_multiplier`, `charge_on_sight` (полуторная дальность обнаружения и
отказ от минимальной дистанции удержания) и `sprite_tint`; у всех них нейтральное
значение (1.0 / false / белый), поэтому волк и культист играют ровно так же, как
до появления этих параметров.

**Читаемость (`CRITIC-P1-09/-18`).** Телеграф собран по правилу «заливка плюс
жёсткий контур»: холодная голубая `TELEGRAPH_FILL` поверх непрозрачного
почти-чёрного `TelegraphOutline` — это соседний `ColorRect` на `z_index` ниже
заливки (не ребёнок: рампа альфы едет по `telegraph.modulate.a`, и ребёнок
увядал бы вместе с ней). Альфа ramp'а 0.70 → 0.95: первый кадр уже различим
≥ 3:1 на самом тёмном полу игры (подземелье), контур — ≥ 3:1 на самом светлом
(лес). В `_ready` экспортированный `sprite_tint` перекрашивается под зону
спавна: оттенок типа берётся из `Enemy.READABLE_TINTS` (23 типа), а яркость —
из множителя зоны (`enemy_body_tint()`), поэтому один и тот же враг остаётся
узнаваемым по цвету, но подстраивается под светлый или тёмный пол. Спрайту
выдаётся `ShaderMaterial` силуэта: 1 px обводки, развёрнутой из альфы спрайта
(четыре тапа на пиксель 16×16, программа одна на весь ростер), а цвет обводки
задаёт зона (`enemy_outline_color()`): тёмная на светлых полах (лес, руины) и
светлая на тёмных (подземелье, крепость). Метрика читаемости — разрыв силуэта,
а не «оттенок ИЛИ контраст»: пиксель тела считается отделённым, если он даёт
≥ 3:1 к полу или граничит с таким пикселем (почти чёрные пиксели волка
физически не поднимаются множителем до 3:1 на тёмном полу, но читаются как
контур); тест `enemy_roster` собирает реальные пиксели композита по атласам зон
и требует ≥ 90 % отделённых, обводку ≥ 3:1 и ≥ 50 % прямых — без лазейки по
оттенку. Полосатая плита шипастой ловушки (`spike_trap.gd`) живёт тем же
правилом: покой — приглушённая бирюза альфой ровно 0.5 (боты читают `a > 0.5`
как «идёт предупреждение» — выше нельзя), предупреждение — общий голубой
0.6 → 0.95 поверх тёмного контура (`show_behind_parent`), открытые шипы —
отдельный тяжёлый цвет. Тяжёлые замахи боссов используют `HEAVY_TELEGRAPH_COLOR`
(ярко-пурпурный), фаза 2 капитана — насыщенный фиолетовый
`PHASE2_TELEGRAPH_COLOR`; кольца опасностей Звонаря и Короля рисуются парой
`draw_arc` — тёмный контур под цветной дугой.

Одна поправка на движок: эта сборка Godot называет локальный материал
`CanvasItem` свойством `material` (с `use_parent_material`), а не
`material_override` из 4.x — проверка по живому списку свойств; присваивание
`material_override` падает в рантайме с «Invalid assignment of property or
key». В шейдере та же сборка ждёт `TEXTURE_PIXEL_SIZE`, а не `PIXEL_SIZE`.

### Боссы

`Boss` (`scripts/ai/boss.gd`) наследуется от `Enemy` и не дублирует FSM: весь
цикл состояний, телеграф, хитбоксы и `DamageResolver` остаются базовыми, а босс
подменяет ровно три точки. `phase_two_health_fraction` (по умолчанию 0.5) —
порог ярости, он считается один раз от `max_health` и в фазу 2 возвращается
только через `_phase >= 2`, поэтому откат лечения назад фазу не меняет; при
переходе босс добавляет себе `enraged_speed_multiplier` и
`enraged_cooldown_multiplier` поверх уже выставленных в сцене множителей типа.
Тяжёлый замах — это счётчик: `_swing_counter % HEAVY_SWING_EVERY == 0`, то есть
каждый третий, а не случайность и не таймер; множители урона и замаха берутся из
констант, а `windup_multiplier` базового класса одалживается на один замах и
обязательно возвращается, когда состояние ATTACK заканчивается, — иначе следующий
обычный замах остался бы медленным. Стаггер закрыт переопределением `_enter()`:
базовый `receive_damage()` сначала пишет `_stagger_bonus` из блока `combination`
пришедшего удара и только потом просит STAGGER, так что «обычный удар не сбивает,
связка лёд+физика сбивает» — это проверка `_stagger_bonus > 0.0`, а не отдельный
список типов урона.

Хранитель леса (`scenes/enemies/forest_warden.tscn`) — первый босс: 180 hp,
16 урона, коробочка тела больше волчьей (18x14 против 12x10), `speed_multiplier`
0.85, награда 120 xp / 60 золота и `echo_amulet` со 100% шансом. Ставится в
`forest.gd` последним спавном у дальней восточной стены: боты (BOT-008, BOT-010)
ищут цель в радиусе заведомо меньше `LEASH_RADIUS` босса, поэтому разнести босса
по отдельной ветке проверки не требуется.

Ещё трое (§11) наследуются от того же `Boss` и не трогают ни `Enemy`, ни `Boss`:
каждый подменяет `_enter_phase_two()` (а Капитан ещё и `_start_attack()`), дописывая
к базовой ярости свою механику второй фазы. Корневая Матерь (`root_mother.tscn`,
лес, 260 hp): в фазе 1 ставит паука каждые `summon_interval` секунд, не больше
`max_minions` живых и только пока игрок в `summon_radius`; ниже половины перестаёт
звать и выпускает два `InfectedNode` рядом с собой. `scripts/world/infected_node.gd`
— не враг, а `StaticBody2D` с `HealthComponent`: solid на слое мира и одновременно
на слое, который слушает хитбокс игрока, чтобы в узел можно было ударить; не ходит,
не бьёт, не в группе `enemy`, xp не платит. Пустой пул → флаг на `GameState`, тост,
сигнал `destroyed` боссу. Оба узла срублены → однократный `weaken()` (не идемпотентен
был бы баг: второй узел или поздний дубль ещё раз притупил бы босса): урон ×0.6,
скорость ×0.75. Капитан Погребальной Стражи (`captain_of_the_guard.tscn`, руины,
300 hp): `frontal_block` 0.6 в фазе 1, в фазе 2 навсегда 0.0, телеграф перекрашивается
в более холодный цвет, а тяжёлый замах падает каждый второй вместо третьего
(`HEAVY_EVERY_PHASE_TWO`, оверрайд `_start_attack` после базового подсчёта). Звонарь
Пустой Крипты (`bell_ringer.tscn`, подземелье, 340 hp, дальний): независимо от
базовой стрельбы каждые `WAVE_INTERVAL` бьёт по игроку радиальной волной в
`WAVE_RADIUS`; ниже половины сверху роняет по два тлеющих круга-ловушки за волну, не
больше `HAZARD_MAX` живых. Волна и круг — короткие узлы-однодневки (как лужа
`death_pool` у чумного), сами себя освобождают по таймауту; урон средовый, через
`DamageResolver` с `null`-атакующим, чтобы мёртвый посреди DoT босс не оставил статус
на освобождённой ссылке. Радиус — обычная проверка дистанции до единственного
игрока, а не `Area2D`: обещание «внутри кольца / снаружи» тогда проверяемо напрямую,
не завися от того, когда физический сервер заполнит оверлапы.

Финальный босс (§11.4) — Король Без Венца (`king_without_crown.tscn`, крепость,
600 hp, `scripts/ai/boss_king.gd`). Единственное место, где `Boss` не просто одалживается,
а расширяется: базовый класс знает один порог, а Королю нужны два, поэтому оверрайдом
идёт `_on_pool_changed` (обе границы считаются из `phase_thresholds()` → `[0.66, 0.33]`),
а `_enter_phase_three` добавляет третий шаг. Базовый `_enter_phase_two` по-прежнему
владеет яростью второй фазы (один раз мноит экспорты), так что третья фаза лишь доводит
скорость до `PHASE3_SPEED_TOTAL` (1.5× от базовой), а не перекладывает ярость заново. Обе
границы — односторонние двери, как и базовая: откат лечения назад не стакает множители и не
переизлучает `phase_changed`. Фаза 2 — радиальная пепельная волна каждые `WAVE_INTERVAL`
(ожог), фаза 3 заменяет её тремя пепельными столбами за волну (порча, не больше
`PILLAR_MAX` живых) и переносит тяжёлый замах на каждый второй (оверрайд `_start_attack`,
как у Капитана). Волна и столбы — узлы-однодневки со средовым уроном через
`DamageResolver` с `null`-атакующим, ровно как у Звонаря. Смерть Короля ставит флаг
`king_defeated` и тост «Король пал» — это единственный игровой ключ, отпирающий трон, —
и всегда отдаёт `rusted_seal` (`loot_chance = 1.0`): без этой печати одна из трёх судеб
незаперта только формально, а на деле недостижима.

Трон (`scripts/world/ending_altar.gd`, `EndingAltar extends Area2D`) стоит в глубине
святилища, в двух тайлах от тела. Как и выход из зоны, он `interactable` без обработчика
оверлапов: на него наступают, но ничего не происходит. Пока `king_defeated` не выставлен,
`interact()` отвечает тостом «Сначала победите короля» и больше ничем. После — открывает
настоящую панель выбора у HUD (`Hud.open_ending_choice(altar)`), а не тост: три судьбы
списком с курсором `>`, навигация `↑↓`, подтверждение `E`, выход `Esc`, и пока панель
открыта держится `ui_blocking`. Первый кадр ввода глушится, как у бегунка диалогов, иначе
клавиша `E`, открывшая трон, тут же подтвердила бы первую судьбу. Перед открытием панель
гасит все модальные окна, с которыми могла бы наложиться, а в `_process()` стоит раньше
веток остальных панелей: пока она открыта, `↑↓`/`E`/`Esc` достают только её, чужой залп
клавиши умирает вместе с кадром-снимком, и поверх трона ничего не откроется.

Панель ничего не знает о сюжете: она спрашивает у алтаря `ending_ids()`,
`ending_description()`, `ending_is_available()` и `ending_lock_reason()` и рисует
«доступно» или «закрыто: <причина>». Развязка заперта не целиком, а двумя третьими:
`dawn` открыт сразу после смерти Короля, `memory` требует `pilgrim_truth_known`
(«Нужно узнать правду о печати»), `crown` — и правды, и `rusted_seal` в инвентаре
(«Нужна печать короля»). Тот же `_lock_reason()` проверяет и `choose(ending_id)` —
единственный шов, пишущий финал: он принимает ровно `dawn`/`memory`/`crown`, ровно один
раз, при отказе отдаёт причину в тост и ничего не пишет. Условие и его отображение
сидят в одном месте именно поэтому: панель не может пообещать судьбу, которую алтарь
откажется выдать. Записав судьбу, `choose()` пишет `GameState.ending` (первое поле,
сериализуемое в сохранение, в отличие от флагов `ending_<id>`) и зовёт `Hud.show_victory`.
Успех намеренно не зовёт `_recompute_ui_blocking()`: блокировку и паузу после этого
перехватывает экран победы, а не панель выбора, иначе подтверждение вернуло бы ввод
игроку в уже оконченный мир. Сам экран победы алтарь не рисует и терминален —
подтверждение ведёт не «закрыть», а в главное меню (`return_to_menu`), потому что в
оконченный мир возвращаться некуда.

Полоса босса берёт цель не из сигнала, а из группы `boss`: `Hud` раз в кадр
перебирает группу и берёт ближайшего живого босса, пока игрок внутри
`BOSS_ENGAGE_RADIUS` (200 px). Ближайшего, а не первого: в лесу теперь два босса
(Хранитель и Корневая Матерь), и `get_first_node_in_group` показал бы полосу того,
что стоит дальше, пока игрок дерётся с этим. Разрешение цели пересчитывается каждый
кадр, поэтому полоса сама переходит с одного босса на другого, если игрок отойдёт.
Группа вместо ссылки — чтобы `Hud` не зависел от того, какой мир сейчас собран и
сколько в нём боссов. Живость проверяется по `HealthComponent.is_dead`, а не по
наличию узла: труп гаснет 0.45 с через `Tween` и всё это время висит в дереве, так
что одной проверки на `null` хватило бы, чтобы полоса пережила собственного босса.

### Черты поведения

Семь новых экспортов `Enemy` — те же механические рычаги, а не новые скрипты:
нейтральное значение каждой черты (0.0 / false / "") совпадает с поведением
волка и культиста, поэтому черта молчит, пока сцена её не включила.
`frontal_block` — рыцарь: гасит долю удара, пришедшего в конус 70° от направления
взгляда. `aura_heal_per_second` — культист: раз в секунду лечит союзников в
радиусе 70 px, не больше 8 за тик. `death_pool` — чумной: оставляет на трупе
лужу `blight` на 4 с, не больше трёх живых луж сразу. `stationary` —
корнезвер: не ходит, но бьёт всё, что вошло в `attack_range`; поворот к
игроку остаётся, выключены только ноги. `teleport_interval` — мигун: в погоне
прыгает на 40–70 px и 0.15 с после прыжка ловит урон с множителем 1.5.
Размах 40–70 px — правило, а не намерение: точка приземления отвергается, если
на ней твёрдая плитка или тело, которое враг видит по своей `collision_mask`
(иначе `move_and_slide` вытолкнул бы тело из наложения в том же кадре, и к
прыжку добавилось бы выталкивание), а длина прыжка пишется в
`last_teleport_distance` и отдаётся сигналом `blinked`.
`web_on_hit` — паук: попавшая ближняя атака вешает `chill` на указанное число
секунд через общий `StatusComponent`. `pack_bonus` — стая: каждый живой
союзник в радиусе 90 px добавляет к скорости, суммарно не выше 0.4; подсчёт
обновляется раз в 0.25 с и читается из кэша, чтобы `_physics_process` не
аллоцировал.

### Ростер: восемнадцать обычных типов

§10 требует не меньше восемнадцати механически разных типов обычных врагов, и
перекрашенный моб под это требование не подпадает. Сейчас их восемнадцать плюс
Хранитель леса, и различаются они именно набором черт. Группа `enemy_roster`
собирает из каждой сцены `scenes/enemies/*.tscn` кортеж `(kind, speed_multiplier,
attack_cooldown_multiplier, windup_multiplier, frontal_block,
aura_heal_per_second, death_pool, stationary, teleport_interval, web_on_hit,
pack_bonus)` и требует, чтобы восемнадцать кортежей дали восемнадцать разных
строк. `display_name`, `sprite_tint`, `max_health` и `attack_damage` в кортеж не
входят намеренно: это ровно те поля, которые меняет перекраска, и проверка,
которая их учитывает, пропустила бы перекрашенного моба как нового. Боссы из
подсчёта исключены явно, списком имён типов, и тест проверяет, что исключены ровно
эти четверо, — молча отбросить строку было бы проще, но не честнее. Без явного
списка Звонарь по кортежу совпал бы с обычным лучником и просочился бы как
перекраска, хотя босс — не обычный тип.

Лес, девять типов: `ash_wolf` (ближний по умолчанию, с которого сняты все замеры),
`ash_archer` (дальний по умолчанию), `ash_boar` (`charge_on_sight`), `ash_wisp`
(1.5 скорости при кулдауне и замахе 0.7), `spider` (`web_on_hit` 1.2 с `chill`),
`slime` (0.45 скорости и `death_pool` `blight` на 3), `tick` (`pack_bonus` 0.12 —
трое в радиусе 90 px бегут быстрее одного), `lumberjack` (`windup_multiplier` 1.8
при 15 урона — самый читаемый замах в игре) и `root_beast` (`stationary`: не
сдвигается с корня ни на пиксель, но бьёт всё, что вошло в 18 px).

Руины, три типа: `ruin_skeleton`, `ruin_skeleton_archer` и `cultist_caster`
(`aura_heal_per_second` 3 в радиусе 70 px — единственный целитель в игре, поэтому он
и остаётся за запертой дверью: арена-бот приходит в этот зал именно за
поддерживающим врагом). Скелет-лучник до роста ростера был дословной перекраской
культиста-стрелка: тот же кортеж, другие цифры и оттенок — ровно то, что §10 не
считает. Теперь он тяжёлый лучник: 0.85 скорости, `attack_cooldown_multiplier`
1.3 и `windup_multiplier` 1.35, то есть медленнее, реже стреляет и дольше
предупреждает, а культист остаётся быстрым.

Подземелье добавляет три типа: `bone_crawler` (1.35 скорости, низкий хитбокс),
`plague_bearer` (`death_pool` на 5 урона: труп становится лужей, в которую нельзя
встать) и пару `grave_hound` (`pack_bonus` 0.15, охотится парой). Крепость добавляет
`ash_knight` (110 hp, `frontal_block` 0.45, держит коридор лицом), `shieldbearer`
(`frontal_block` 0.6 — сзади по нему проходит в два с половиной раза больше) и
`royal_guard` (`attack_cooldown_multiplier` 0.85, замах 1.3 и щит 0.25). Четверо —
гончие, щитоносец и королевский страж — раньше дебютировали в зале руин; замечание
критика D4-R3 состояло в том, что последние две зоны мира приносили почти ничего
нового (подземелье два типа, крепость один), поэтому они переехали глубже: пёс
держит склеп, двое воинов — крепость, и каждая из двух глубоких зон вводит не меньше
трёх невиданных раньше типов. Целитель же остаётся в руинах: на нём держится роль
поддержки в арене `BOT-003`, который спускается только в зал руин, а не в склеп.

### Кривая сложности по зонам

Пул обычных врагов обязан расти по мере продвижения вглубь, иначе последний боец
ростера слабее среднего бойца середины игры и игрок это чувствует. Порядок
задан явно и закреплен тестом `enemy_roster`, который считает среднее
`max_health` по **обычным** постам спавна каждой зоны; боссы в среднее не входят
ни при каком раскладе — у них своя кривая (180 / 260 / 300 / 340 / 600), и
подмешать их в среднее означало бы измерить не ростер, а список боссов.

Замер, который печатает тот же тест (посты обычные, среднее по обычным):

| зона | обычных постов | обычных типов | среднее hp |
| --- | --- | --- | --- |
| лес | 18 | 9 | 27.78 |
| руины | 7 | 3 | 32.57 |
| подземелье | 14 | 6 | 35.86 |
| крепость | 17 | 10 | 41.71 |

Тест требует, чтобы кривая нигде не переворачивалась: каждая следующая зона не ниже предыдущей,
подземелье лежит в коридоре 34–40 (ниже — подземелье ровесник руин, выше —
к реваншу крепости уже не дорасти), крепость строго выше и подземелья, и руин.
Отдельно закреплено, что одних только **постов** в подземелье не меньше 12, в
крепости не меньше 16, и что обычных **типов** в крепости не меньше восьми и не
меньше, чем в лесу: плотность финала — это не только цифры урона, но и то,
сколько разных противников игрок встречает до трона.

Цифры правятся в двух местах одновременно, и тест это ловит: статы лежат в
`scenes/enemies/*.tscn` (в каждой сцене два вхождения `max_health` — экспорт
`Enemy` и подпись лута, и разъехаться они могут молча), а плотность — в
`_spawn_new_posts` зонных скриптов `scripts/world/dungeon.gd` и
`scripts/world/fortress.gd`. Подземелье получило посты `BONE_CRAWLER_C_ANCHOR`
(28, 26), `PLAGUE_BEARER_B_ANCHOR` (16, 26) и пару `GRAVE_HOUND_A/B_ANCHOR` (30, 13)
и (32, 13) — третий дебютный тип склепа, переехавший из зала руин; крепость —
`ASH_KNIGHT_B` (36, 12), `BONE_CRAWLER_D` (20, 12), `SHIELDBEARER_A` (17, 20),
`CULTIST_CASTER_A` (30, 7), `ROYAL_GUARD_A` (38, 17) и свою пару гончих
`GRAVE_HOUND_A/B` (32, 25) и (30, 25). Все новые якоря проверены
на проходимость и оставлены вне `BOSS_ARENA` крепости (`Rect2i(42, 11, 5, 8)`):
тронный зал обязан приходить пустым.

Новый тип по-прежнему не скрипт: сцена нового врага — это `wolf.tscn` или
`skeleton_archer.tscn` с другим набором экспортов, поэтому все восемнадцать
проходят через одну FSM, один телеграф, один `DamageResolver` и один путь лута.
Единственное, чего ростер требует от новой сцены сверх цифр, — чтобы `enemy_type`
совпадал с именем файла: по этому имени тест и находит сцену, и расхождение
означало бы, что в игру приехал не тот враг.

## Мир

`ZoneBase` (`scripts/world/zone_base.gd`) — общий каркас любой зоны: чтение
сгенерированной сетки (`cell_at`, `map_size`), сборка `TileSet`/`TileMapLayer`
из зонального атласа (путь отдаёт виртуальный `tile_atlas_path()`), отметка
исследованного вокруг игрока, лимиты камеры, детерми-
нированные поиски проходимой клетки, инстанцирование актёров и навешивание
расписаний. Порядок вызова виртуальных хуков зафиксирован в `ZoneBase._ready()`:
`_advertise_zone` → `_generate_map` → `_build_tileset_and_layer` → `_spawn_actors`
→ `_setup_day_cycle` → `_configure_camera`. `Forest` — первая зона,
и в ней остались только данные и контент: сетка, спавны, якоря и `landmarks()`.
Безопасную зону лес потерял вместе с деревней: `safe_zone_owner` теперь носит сам
`Village`, а `Forest.SAFE_ZONE_RECT` доживает приватной запретной зоной у спавна.
Сама бывшая деревенская поляна больше не голая земля: она перекрашена в лагерь,
из которого люди ушли (`_paint_ruined_camp`), — см. абзац про лес ниже.
Вторая зона обязана реализовать лишь `_generate_map`,
`_spawn_actors` и два хука идентичности (`zone_id`, `zone_name`); `Forest` при
этом ничего не отдаёт и не меняет.

### Зоны

По ТЗ §5 в игре пять зон, и все пять — отдельные миры со своей строкой в таблице:
лес, деревня, руины, подземелье под руинами и крепость. Деревня вынесена из леса в
самостоятельную зону `Village` (`scripts/world/village.gd`): у неё своя карта, свой
тайл входа, свои шесть жителей и своя безопасная зона. Маршрут
деревня ↔ лес → руины → подземелье → крепость. Лес — стартовая зона и узел: на его
западной дороге стоит `VillageGate` (в деревню), на восточной — `RuinsGate`
(в руины); дальше каждая следующая зона открывается дверью в предыдущей, а не
пунктом меню.

Список зон живёт в `data/zones.json`, а не в коде: `id`, русское имя, путь к
скрипту мира и тайла входа. Добавление зоны — это новый скрипт-наследник
`ZoneBase` и одна строка в таблице; ни один существующий мир при этом не
правится.

**Пол у каждой зоны свой (`CRITIC-P1-01`).** Раньше все четыре зоны красились
из одного `tiles.png`: трава RGB(173, 188, 58) занимала 65 % / 79 % / 39 % / 92 %
выборки пола в лесе / руинах / подземелье / крепости, и зона различалась только
подписью в HUD. Теперь `ZoneBase.tile_atlas_path()` — виртуальный, и каждая зона
переопределяет его своим атласом: `tiles_forest.png`, `tiles_ruins.png`,
`tiles_dungeon.png`, `tiles_fortress.png`. Файлы порождает
`tools/import_ninja_sprites.py --zone-variants` из базового атласа целочисленным
аффинным сдвигом по яркости с фиксированным дизером (без передискретизации):
средние полы — лес (172, 187, 57), руины (139, 130, 116), подземелье (56, 65, 97),
крепость (115, 95, 68); ни один RGB не держит больше 3.1 % выборки пола, любая
пара полов различима ≥ 1.5:1 (слабейшая пара — руины/крепость 1.61). Тест
`zone_registry` проверяет и объявленные пути, и различие файлов по SHA-256, и
долю доминанты, и попарный контраст — по пикселям самих PNG.

`ZoneManager` (`scripts/world/zone_manager.gd`) — не autoload, а узел, который
`Main._ensure_zone_manager()` создаёт до сборки первого мира и ставит в группу
`zone_manager`. Статические `zone_config`, `has_zone`, `zone_display_name`,
`zone_script_path` и `entry_tile` читают таблицу; `travel(zone_id)` собирает
новый мир, снимает старый с дерева и освобождает его, вставляет новый на место
старого (`move_child(next, hud.get_index())`, чтобы `Hud` остался поверх мира),
ставит `GameState.zone`, зовёт `hud.rebind_world()` и шлёт `EventBus.toast`.
Освобождение — `free()`, а не `queue_free()`: до конца кадра в дереве висел бы
второй `Player`, и любой `get_first_node_in_group("player")` — боты, камера,
хилки — два кадра работал бы по старому игроку.

`ZoneExit` (`scripts/world/zone_exit.gd`) — `Area2D` в группе `interactable` с
`collision_layer = 32`, `collision_mask = 0` и формой, построенной кодом. Никакого
`body_entered`: переход только по `interact()`, иначе игра перелетал бы зону,
коснувшись ворот плечом. Сам переход — `manager.call_deferred("travel", ...)`,
потому что `interact()` вызывается из `_process` игрока, а `travel` освобождает
старый мир вместе с этим игроком: `free()` посреди его же кадра снял бы узел,
который прямо сейчас исполняет код.

`Village` (`scripts/world/village.gd`) — пятая зона ТЗ, 40×26, и единственный мир,
который игрок населяет: шесть жителей с расписаниями, дома Эдрика, Йорека и Милы,
кузница Брана, мельница Сериса, кожевенный двор Альвены, колодец на площади. Карта
авторская, а не генерируемая: `BUILDINGS`, `DIRT` и `TREES` выписаны прямоугольниками
и тайлами, потому что сидовый разброс не может обещать, что дорога дойдёт до ворот.
Прибытие — с восточной дороги на тайл `(36, 12)`, он же `entry_tile` в таблице;
в двух тайлах западнее стоит `ForestGate` обратно в лес. Врагов зона не спавнит
вовсе, а `SAFE_ZONE_RECT = Rect2i(2, 2, 36, 22)` — всё внутри стены: обещание
безопасности держится конструкцией зоны, а не проверкой. Палитра общая с лесом
(`tile_atlas_path()` → `tiles_forest.png`): `CRITIC-P1-01` требует различать четыре
дикие зоны, а не искать свою траву хутору.

`Ruins` (`scripts/world/ruins.gd`) — вторая зона, 40×26, каменный двор с
колоннами по детерминированной сетке. Геометрия выписана константами
(`INNER_WALLS`, `PILLARS`, `DIRT_PATCHES`), а не катится из сида: загадка стоит
на конкретных тайлах, и у сида не должно быть права их передвинуть. Вход из леса —
`RuinsGate` на тайле `(49, 13)`, восточный конец
дороги, спавнится последним в `_spawn_actors`, чтобы Эдрик сохранил первое место
в группе `interactable` и путь ботов не сдвинулся. Обратно — `ForestGate` на
`(3, 11)`, ровно в трёх тайлах от тайла входа, чтобы подсказка не открывалась
под ногами у прибывшего. Точка появления берётся из таблицы и только
проверяется на проходимость (`_entry_spawn_tile`): `ZoneBase._find_walkable_near`
с радиусом вернул бы первую проходимую клетку окна сканирования по строкам, а не
заявленную клетку, то есть унёс бы спавн в другое место.

Загадка зоны стоит на единственном проёме: `INNER_WALLS` оставляют в колонке 14
проход высотой в пять тайлов (`DOORWAY_TOP_ROW`..`DOORWAY_BOTTOM_ROW`), и через
него из входного коридора в зал попасть больше нельзя никуда. `RuinDoor`
(`scripts/world/ruin_door.gd`) — `StaticBody2D` со `collision_layer = 1` без
четвёрки, чтобы `AttackHitbox` с `collision_mask = 4` не нашёл в дверях цель для
удара; форма строится кодом и равна `16 × 16 × opening_tiles`, то есть закрывает
весь проём, а не тот тайл, на котором узел стоит — плита в одну тайлу в проёме в
пять тайлов это столб, а не дверь, и зал открывался бы без ключа. Открытость —
флаг `GameState` `ruin_door_open`, ровно как у сундука, поэтому дверь ездит в
сейв и обратно бесплатно: `_ready()` применяет флаг до первого кадра, и сейв с
поднятым флагом спавнит уже открытую дверь, а `_physics_process` догоняет тело по
флагу на случай загрузки в той же зоне, где `travel` отказался пересобирать мир.
`Mechanism` (`scripts/world/mechanism.gd`) — `Area2D` в группе `interactable` на

(8 px против 16 px при радиусе 26 px), поэтому ближайшим объектом под ногами
оказывается он, а не дверь. Рычаг называет цель строкой — `requires_item` и
`sets_flag`, — и ищет дверь по группе и совпадению `open_flag`, а не по пути к
узлу; ключ `ruin_key` тратится ровно один раз (`consumed`), повторное
нажатие говорит «Уже открыто» и не тратит ничего. Ключ лежит в `(11, 23)`, в
достижимой половине карты: запертая дверь не должна превращаться в стену.
Шесть скелетов (`scenes/enemies/skeleton.tscn`, `skeleton_archer.tscn`) стоят в
зале за плитой, каждый не ближе шести тайлов от точки входа, и луч
`Enemy._player_visible()` по единице того же слоя не видит игрока сквозь закрытую
дверь. Вторым проходом, `_spawn_new_posts` между скелетами и спуском, в том же зале
встаёт ещё один: `cultist_caster` — тот же якорь, тот же `_find_prop_tile` и тот же
`reserved`, который скелеты заполнили до него, поэтому заклинатель не может встать
на клетку скелета, на рычаг или под ноги прибывшему. Он единственный целитель в игре
и остаётся за дверью: на нём держится роль поддержки в арене `BOT-003`, который
спускается только в зал руин. Двое прежних воинов зала — `shieldbearer` и
`royal_guard` — и пара `grave_hound` по замечанию критика D4-R3 переехали глубже, в
крепость и склеп, чтобы последние две зоны мира вводили новых врагов, а не
перечисляли ростер руин. Квестодатель зоны — `QuestStone` (`scripts/world/quest_stone.gd`),
`Area2D` в группах `interactable` и `quest_stone`: не `Npc`, потому что у плиты
нет ни лица, ни расписания, ни прогона `DialogueRunner`, — и идёт он по легаси-пути
напрямую через `QuestManager`, держа `quest_ids = ["q04_bone_guard",
"q05_ruin_key"]` и отдавая задания строго по одному: сначала сдача готового, потом
отчёт по начатому, и только потом новое. Стоит на `(11, 14)`, на ближней стороне
двери и в восьми тайлах от точки входа, чтобы квест был поводом дойти до зала, а не
наградой за уже решённую загадку. Второй квестодатель склепа — Нела (`Villager`,
`NELA_ANCHOR = (16, 6)`, `q11_light_the_way`): в отличие от плиты это живой `Npc`
без расписания (в склепе нет `DayClock`), в восьми тайлах от входа и вне плит-
ловушек, врагов и лестницы; задание отдаёт легаси-путём, реплик в
`data/dialogue.json` для неё нет.
   `landmarks()` отдаёт
пять типов — `gate`, `door`, `mechanism`, `key`, `tablet`, — и `key` выпадает из
списка сам, когда подбираемый предмет освобождает себя. У `Pickup` есть
`taken_flag`: непустой записывается в `GameState` при подборе, и пересобранная
зона, прочитав его, не респавнит уже взятую находку (ключ руин несёт
`taken_flag = "ruins_key_taken"`), тогда как обычный луфт с пустым флагом
возвращается вместе с зоной, как раньше.

`Dungeon` (`scripts/world/dungeon.gd`) — третья зона, 44×28, подземелье под руинами:
то, за что игрок платит ключом, а не ещё один коридор. Планира выписана константами
так же, как у руин — `WALL_BLOCKS` (8 кладок), `PILLARS` (12 колонн), `DIRT_PATCHES`
(5), `CHOKEPOINT_STUBS` (4), `ALCOVES` (3 ниши), — но руины это зал, а по ТЗ §5.1
здесь нужны петли. Поэтому карта собрана как отрицательное пространство восьми
кладок: три горизонтальных коридора (строки 1..3, 12..14, 24..26) и четыре
вертикальных (колонки 1..3, 12..14, 24..26, 37..39), каждый в три тайла. Каждый
перекрёсток — способ объехать, и именно это делает граф цикличным, а не деревом
тупиков: 591 проходимый тайл и 960 рёбер соседства против 590 необходимых. Четыре
пенька `CHOKEPOINT_STUBS` выдаются в грань кладки и сужают коридор до двух тайлов,
никогда его не перекрывая, — на этих сужениях стоят обе `SpikeTrap`, `(17, 12)` и
`(24, 10)`, там игрок видит противоположную сторону прежде, чем шагнуть. Ниши
вырезаются уже после кладки, поэтому вырезка — отдельная покраска, а не отсутствие
стены. Что зона не делится надвое одним узлом, проверено тестом: если заблокировать
перекрёсток колонок 12..14 на строках 12..14, в `(24, 13)` всё равно дойти — 43 шага
против 25 прямых.

Спуск — `DungeonGate` на тайле `(37, 22)`, в зале за плитой; спавнится он после
скелетов (`_spawn_dungeon_gate` в конце `_spawn_actors`), чтобы не сдвинуть их якоря
и первые места в группе `interactable`. В `landmarks()` руин его намеренно нет:
тесты руин держат ровно пять landmark и фиксированный список типов, а требование
было за landmarkами подземелья, не руин. Обратно ведёт `RuinsExit` на `(2, 10)`, и
он один: двери в лес отсюда нет, дорога назад лежит через руины, поэтому
`landmarks()` подземелья отдаёт три записи — `gate` и два `trap`. Новых типов landmark
не понадобилось: `MapPanel` уже рисует и ворота, и ловушки.

Врагов десятеро — три `ruin_skeleton`, два `ruin_skeleton_archer`, два `ash_wisp`,
двое `bone_crawler` у дальней стены и `plague_bearer` у северного прохода.
Первые семеро ставятся по якорю через `_find_prop_tile`: ближайший проходимый и уже
достижимый из входа тайл, не ближе шести тайлов от точки входа и не на тайле другого
врага, поэтому ни один страж не приезжает под ноги прибывшему. Трое новых идут
вторым проходом — `_spawn_new_posts` после `_spawn_enemies`, — тем же
`_find_prop_tile` и с тем же `reserved`, который первая волна заполнила до них, так
что якорь нового врага физически не может сесть на чужую клетку или на лестницу.
Якоря подобраны так, что шеститайловое расстояние сохраняется и до шипастых плит, и
до обеих лестниц: держат это не отдельная константа и не отдельная проверка в
поиске, а тесты подземелья, которые перебирают всех врагов зоны, — сдвинуть якорь на
плиту значит уронить тест, а не выпустить врага под ноги. `SpikeTrap` в группу
`interactable` не входит — это опасность, а не предмет разговора, и тест ищет её по
детям зоны, а не по группе. Часы `DayClock` подземелью нужны свои: строка времени в
`Hud` читает мир через группу `day_clock`, и без часов она просто опустела бы, пока
игрок под землёй. Неба здесь нет, но строка — не небо.

`Fortress` (`scripts/world/fortress.gd`) — четвёртая зона, 48×30, Древняя крепость
на конце дороги: то, к чему шёл весь маршрут, а не ещё одна карта, в которой можно
заблудиться. Если руины — зал, а подземелье — сеть, то здесь ряд комнат:
двор → казарма → архив → тронный зал → сломанное святилище, по ТЗ §5. Четыре
разделительные стены (`INNER_WALLS`) режут сетку на пять названных областей, и
каждая написана двумя прямоугольниками так, чтобы строки 14..15 оставались
открытыми — этот проём в два тайла против дороги в два тайла и есть единственная
дверь, поэтому в зоне нет ни одной односторонней геометрии: ни дверей, ни рычагов,
ни обвалов. Строки `SPINE_TOP_ROW`/`SPINE_BOTTOM_ROW` — обещание зоны, и тест меряет
их по тайлам от западной стены до восточной, а не выводит из констант стен, потому
что стены — ровно то, что ломает правкой. Остальная кладка — острова: фундаменты
хижин и огрызок куртины во дворе, четыре барака в казарме, шесть стеллажей в
архиве, два подиума в тронном зале; ни один из них не касается ни внешней стены, ни
другого острова, поэтому ни одна комната не делится на два кармана. Колонны у проёмов
стоят на тайл от проёма и на строку от строки спайна — ворота выглядят воротами, а не
сужением. 1080 проходимых тайлов, все 100 % достижимы из точки входа `(4, 14)`.

Назад ведёт `DungeonExit` на `(2, 11)`, в трёх тайлах от точки входа, и он один:
двери в лес или руины отсюда нет. Вверх — `FortressGate` в `Dungeon` на `(42, 1)`,
в дальнем северо-восточном углу подземелья: 50 шагов от лестницы против 25 через
зону, десять тайлов от ближайшей плиты, колонны или стража, и спавнится он последним
в `_spawn_actors`, после всех якорей, — тем же порядком, каким руины ставят свой
спуск. Дверь намеренно не landmark, ровно как руины не метят свой спуск: путь
дальше — награда за пройденное подземелье, а не точка на карте. `landmarks()`
крепости отдаёт пять записей — `gate` и четыре `room`, — и это первый новый тип
landmark со времён руин: у `room` своя ветка `match` и приглушённый сланцевый цвет,
потому что комната — это земля, а не предмет на ней. Четыре метки строятся из
`ROOM_BOUNDS` при каждом вызове, а не кэшируются: земля не освобождает себя, так что
живая ссылка узла ей не нужна.

Гарнизон — десять врагов: два `ruin_skeleton` во дворе, два `ruin_skeleton_archer` и
`ash_boar` на плацу казармы, два `ash_wisp` и третий лучник у архива, где за
стеллажами есть чем разорвать линию взгляда, `ash_knight` на плацу и
`bone_crawler` в архиве. Ставятся те же
`_find_prop_tile` по якорю, не ближе шести тайлов от входа: двое новых идут
отдельным `_spawn_new_posts` сразу за первой волной и тем же `reserved`, поэтому
кольцо святилища, уже заложенное туда до расстановки, остаётся занятым и для них.
Дальний конец дороги —
пол святилища за последним проёмом — оставлен пустым:
`BOSS_ARENA = Rect2i(42, 11, 5, 8)` — 40 тайлов голого камня, которые попадают в
`reserved` тайл за тайлом до расстановки врагов, так что кольцо удерживается тем же
механизмом, что не даёт двум врагам встать на одну клетку, а не правилом, которое
каждый будущий спавнер должен помнить. Финального босса в игре ещё нет, но земля под
него есть, и добавлять его придётся, а не расчищать.

Квестодатель крепости — Орен (`Villager`, `OREN_ANCHOR = (21, 10)`,
`q12_officers_seal`: снять пепельного рыцаря). Ставится `_spawn_oren` после
`_spawn_new_posts` и до финального босса тем же `_find_prop_tile` по якорю, не ближе
восьми тайлов от входа и вне `BOSS_ARENA`, чтобы не встать в кольцо, оставленное под
босса. Как и Нела, это живой `Npc` без `ScheduleComponent` (в крепости нет
`DayClock`) и без реплик в `data/dialogue.json` — задание отдаётся легаси-путём.

Зона — часть сохранения. `GameState.zone` пишется в слот рядом с позицией, а
`SaveManager.slot_zone(slot)` читает из слота только её, без загрузки сейва.
Порядок восстановления обратен порядку записи: `Main._apply_pending_load()` и F9
в `Hud` подглядывают зону через `slot_zone`, переходят в неё через `travel` и
лишь потом грузят слот — иначе `EventBus.save_loaded` посадил бы сохранённую
позицию на игрока, который стоит в чужой зоне, и точка пропала бы в стене.
`GameState` читает таблицу своим маленьким загрузчиком (`_zone_ids_known`,
`_restore_zone`), а не через `ZoneManager`: `zone_manager.gd` ссылается на
autoload-ы `GameState` и `EventBus`, и обратная ссылка autoload-а на `class_name`
замкнула бы цикл компиляции.

`Hud` держит зону строкой `Зона: <имя>` под полосами и обновляет её по переходу,
`MapPanel.set_world()` переключается на новый мир (метод идемпотентен и не
дублирует заголовок), а ворота рисуются на карте отдельным типом landmark —
`gate`. Типов landmark семь: `gate`, `door`, `mechanism`, `key`, `tablet`, `room` и те,
что отдаёт
`Forest`. У каждого своя ветка `match` со своим цветом, и незнакомый тип не
рисуется никак, так что новый landmark появляется на карте только вместе с
собственной веткой.

`Forest` (`scripts/world/forest.gd`) собирает карту из детерминированного сида:
`TileSet` создаётся в рантайме, у камня и дерева есть коллизия. Спавны описаны
в одном месте, координаты в тайлах.

Западная поляна, где когда-то стояла деревня, больше не закрашена землёй целиком:
`_paint_ruined_camp` красит `CAMP_RECT = Rect2i(2, 6, 8, 6)` обратно в траву и
ставит на неё следы ушедшего поселения — фундаментный мусор `CAMP_RUBBLE` (5
одиночных `#`-камня) и заросли `CAMP_THICKET` (3 куста `T`), которые лезут в
щели между камнями. Раскладка целиком авторская, ни одного броска ГПСЧ лагерь
не делает, поэтому кластеры деревьев, волчьи посты и шея под завалом стоят ровно
там же, где стояли: замер показал 0 изменённых тайлов вне `CAMP_RECT`.

Форма этой раскладки выведена не из вкуса, а из того, как четыре тайла атласа
выглядят рядом: снимок rect'а сложен из самих тайлов и показал два правила.
`,` — это тайл дороги, поэтому земля внутри rect'а, не соединённая с дорогой,
читается как та же мёртвая рыжая дыра, только меньше; лагерь не красит землю
вовсе, и единственное потоптанное место внутри него — дорога, которая потоптана
по делу. `#` — плоская серая плита, и два камня встык сливаются в одну серую
ленту, а прямая лента одного тайла через всю карту — это тот же дефект, что и
прямоугольник, только в другом цвете; поэтому ни один камень не касается другого
по стороне. Оба правила — проверки в тесте, а не комментарий.

Столы и кусты не ставятся ближе `CAMP_CLEAR_FROM_SPAWN = 3` тайлов (Чебышёв) к
тайлу прибытия: столб в двух тайлах юго-восточнее спавна закрывал угол, через
который игрок выходит по диагонали, и срезал пятую часть диагональной скорости.
И держатся двух строк `CAMP_PROP_ROW_TOP`..`CAMP_PROP_ROW_BOTTOM` к северу от
дороги: всё южнее — полоса движения, по которой боты идут на волков и обратно к
`VillageGate`, и камень, поставленный в неё, выглядит в логе бота не как
декорация, а как повторяющийся `watchdog_stuck` до прогона (так BOT-008 и упал).
Сама проверка живёт в `_paint_camp_solid` и ругается вслух, а не красит
исподтишка. Раскладка читается тестом через `camp_layout()` — метод узла, а не
константа класса: ссылка на `Forest` из тестов затянула бы `forest.gd` и всё под
`ZoneBase` в единицу компиляции теста, где автозагрузки уже не идентификаторы.

Помимо двух сундуков в мире лежат четыре подбираемых предмета (`PickupA`,
`PickupHerb`, `PickupCoin`, `PickupFlask`) и завал `Breakable`
(`scripts/world/breakable.gd`, `scenes/world/breakable.tscn`) на тайле
`RUBBLE_TILE = (19, 28)`. Завал — `StaticBody2D` со `collision_layer = 5`:
единица блокирует игрока, четвёрка подставляет его под `AttackHitbox`, у
которого `collision_mask = 4`. Разрушаясь, он снимает коллизии в том же кадре
(`queue_free` отвязал бы тело только в конце физического шага, и игрок, уже
идущий в кучу, отбивался бы от неё) и ставит флаг
`shortcut_forest_south_open`. Ниша `PickupFlask` в `(20, 30)` без завала — 41
тайл в обход против 37 через пробитый проход.

### Деревня и безопасная зона

Деревня — самостоятельная зона, и безопасная зона живёт в ней, а не в лесу.
Граница живёт в `Village.SAFE_ZONE_RECT = Rect2i(2, 2, 36, 22)` (тайлы), проверка —
`Village.is_in_safe_zone(tile)`. Владелец — сам `Village`, который в
`_advertise_zone` встаёт в группу `safe_zone_owner`, поэтому правило не привязано к
конкретной карте: любой мир может стать владельцем зоны. `Forest` из группы вышел
вместе с деревней и ничего не обещает: его
`SAFE_ZONE_RECT = Rect2i(2, 5, 9, 8)` доживает приватным запретом у точки спавна и
на поведение врага не влияет: на этих тайлах теперь лагерь ушедшей деревни, и
ни один новый хищник и паломник на них не ставится, потому что через них идёт
дорога к `VillageGate`.

Правило для врага реализовано в `Enemy` (`scripts/ai/enemy.gd`) и действует в
обе стороны. Перед `move_and_slide` вызывается `apply_safe_zone_movement`: если
шаг выводит врага в зону — скорость по этой оси обнуляется (враг упирается в
границу и не переступает её), а если враг уже внутри — он разворачивается и
идёт к ближайшей границе или к точке спавна, то есть выходит из зоны. Атаку из
зоны враг не начинает: проверка `not _inside_safe_zone()` стоит на входе в
атаку. Владелец зоны ищется через `get_first_node_in_group("safe_zone_owner")`
и кэшируется, так что на голой арене без владельца враг ведёт себя как раньше.

Четвёртый житель — травница Мила. Это `Villager`
(`scripts/npcs/villager.gd`, `class_name Villager extends Npc`) с подсказкой
интеракта «Поговорить» и списком заданий `quest_ids` (`q02_gather_fangs`,
`q03_clear_boars`): сначала прогон диалога, затем легаси-выдача квеста. Спрайт
у неё зелёный (травница), строится кодом при спавне. Ставится она в деревне
`_spawn_villager` на авторский тайл `MILA_TILE = (16, 9)`, после Эдрика, Йорека и
Брана, чтобы первым в группе `interactable` оставался Эдрик и путь ботов (BOT-001,
BOT-002) не изменился.

Пятый и шестой жители — `SERIS_TILE = (12, 16)` (Серис, мельник, `q09_the_mill`:
принести три волчьих клыка) и `ALVENA_TILE = (26, 19)` (Альвена, кожевница,
`q10_armor_fit`: два осколка кости). Оба те же `Villager`, что и Мила, и спавнятся
после неё тем же `_spawn_villager`, поэтому Эдрик по-прежнему первый в группе
`interactable`. Тайлы авторские, а не найденные сканом: карта деревни выписана
вручную, и каждый пост лежит проходимой клеткой не ближе трёх тайлов (Чебышёв) к
соседу и четырёх к Эдрику; три тайла это 48 px, а радиус
интеракта 26 px, поэтому маршрут бота до первого интерактивного объекта не цепляет
новичков. Серис и Альвена носят `ScheduleComponent` и утренние точки в
`schedules.json`, как остальные деревенские.

Двое квестодателей в глубоких зонах — Нела в склепе (`NELA_ANCHOR = (16, 6)`,
`q11_light_the_way`: три костяных ползуна) и Орен в Древней крепости
(`OREN_ANCHOR = (21, 10)`, `q12_officers_seal`: пепельный рыцарь). Это тоже
`Villager`, но без `ScheduleComponent`: в склепе и крепости нет `DayClock`, так что
вести их по фазам некуда, и они стоят на месте. Тайл берётся `_find_prop_tile` по
якорю, не ближе восьми тайлов от точки входа, чтобы квест был поводом дойти вглубь,
а не найденным у двери; в крепости дополнительно вне арены финального босса. Все
четверо новичков выдают задание легаси-путём: для них нет строк в
`data/dialogue.json`, поэтому `Villager.interact` не находит реплик раннера и сразу
берёт/сдаёт единственный квест из `quest_ids` — тот же путь, что у плиты-квестодателя.

Девятый персонаж — Пепельный Паломник (`scripts/npcs/pilgrim.gd`,
`class_name Pilgrim extends Npc`). Это не квестодатель: он не выдаёт ни заданий, ни
наград — только по одному осколку правды о короле в каждой зоне, в порядке сюжета.
Он стоит во всех четырёх зонах (`PilgrimForest`, `PilgrimRuins`, `PilgrimDungeon`,
`PilgrimFortress`) и спавнится последним в каждом `_spawn_actors`, поэтому Эдрик
остаётся первым в группе `interactable`, а маршрут ботов (BOT-001, BOT-002) не
меняется. Серый плащ — `modulate = Color(0.62, 0.62, 0.66)` поверх общего спрайта
NPC (нового файла нет); без `ScheduleComponent` и не является ориентиром на карте.
Метка над головой всегда погашена: `_refresh_bubble` переопределён, потому что
базовый `Npc` подсветил бы её под квест, которого Паломник не даёт. Подсказка
интеракта — «Заговорить», когда новый осколок доступен, иначе «Молчит»; `interact`
открывает дата-драйвенный раннер `pilgrim_<зона>`, а когда раннер отказывает —
произносит одну короткую строку («Он молчит.» если предыдущий осколок ещё не слышан,
«Он уже сказал всё, что помнит.» если этот уже слышан).

Четыре разговора лежат в `data/dialogue.json` (`pilgrim_forest/ruins/dungeon/fortress`,
`speaker_id = "pilgrim"`) и сцеплены флагами по порядку сюжета: лес → руины → склеп →
крепость. Условие каждого — флаг предыдущей зоны И `not_flag` своей, так что осколок
открывается ровно один раз и только после предыдущего; последняя реплика ставит
`pilgrim_met_<зона>`, а финальная в крепости — ещё и `pilgrim_truth_known`, который
читает развязка. Тайлы: лес — якорь `(24, 4)` ВНЕ безопасной зоны через
`_find_pilgrim_tile` (не ближе шести тайлов от входа, в стороне от врагов, реквизита
и других NPC); руины `(9, 8)`, склеп `(12, 12)`, крепость `(29, 17)` — через
`_find_prop_tile` по зарезервированному набору, не ближе шести тайлов от входа, а в
крепости ещё и вне арены финального босса.

### Время суток и расписания

`DayClock` (`scripts/world/day_clock.gd`) — дочерний узел `Forest`, не autoload;
мир-срез владеет им сам. Хранит `time_fraction` от 0 до 1, за кадр продвигает
его на `delta / day_length_seconds` и на смене порога шлёт `phase_changed`.
Такты стоят, пока стоит игра или пока открыт любой интерфейс
(`GameState.ui_blocking`), — во время диалога или меню время не идёт. Фазы и
их начала берутся из `data/schedules.json`, а не зашиты в код.

`ScheduleComponent` (`scripts/npc/schedule_component.gd`) вешается на Эдрика,
Йорика, Брана, Милу, Сериса и Альвену и по `phase_changed` ведёт носителя на тайл
текущей фазы.
Тайл берётся из `schedules.json`, но перед каждым шагом проверяется через
`Forest.cell_at`: шаг делается только по проходимой клетке, поэтому NPC не
заходит в стену и не зависает. Если дойти не выходит (тайл занят или недостижим
за `WALK_TIMEOUT`), носитель телепортируется в ближайшую проходимую клетку
расписания. Носители остаются `Area2D` со `collision_mask = 0`, так что
расписание не создаёт новых физических блокировок проходов.

`data/schedules.json` — единственное место, где правят расписание: `phases`
(4 фазы с `start` от 0 до 1), `npcs` (имя → тайл на фазу),
`day_length_seconds`. HUD рисует строку часов (`Утро · 06:00`) не чаще раза
в секунду; `refresh_clock_line()` вызывается напрямую из теста и скриншот-
пробы, чтобы проверка не зависела от троттла.

## Характеристики

Четыре характеристики (ТЗ §7.1) — Сила, Ловкость, Интеллект, Выносливость — по
5 очков на старте, потолок 30 на характеристику (`MAX_ATTRIBUTE`: без него одну
ветку можно было бы качать до выхода производного числа за пределы играбельного),
2 очка за уровень, потолок уровня 20. Плюс одно очко навыков за уровень
(`skill_points_per_level` там же) — оно тратится на изучение навыков на экране
«Навыки» и отдельно от очков характеристик. Кривая опыта и все коэффициенты лежат в
`data/progression.json`, где `xp_curve[n]` — сколько опыта нужно суммарно на
уровень `n+1`, поэтому настройка прогрессии не трогает код. Единственная точка,
где характеристики превращаются в числа, — `GameState.recompute_derived()`: она
только присваивает (`база + рост уровня + очки характеристики`) и никогда ничего
не прибавляет, поэтому повторный вызов даёт ровно те же числа, а текущие `hp` и
`mana` лишь подтягиваются под новые максимумы. Экипировка входит в пересчёт
только бонусами скорости и сопротивления (`speed_bonus`, `resist_bonus`), и тоже
через присваивание: `total_bonus()` каждый раз заново суммирует надетое по всем
шести слотам, поэтому снятие вещи не оставляет следа. Атака и защита не
кэшируются и читаются там, где используются (`total_attack()`,
`total_defense()`, `Player._magic_damage()`), временные эффекты в пересчёт не
входят вовсе. Сила даёт +1 к атаке за очко,
Ловкость — +0.005 к шансу крита и +0.8% к скорости (потолок 1.3), Интеллект — +4
к максимуму маны и +0.06 к множителю магического урона (пол 1.0, потолок 2.5),
Выносливость — +5 к максимуму здоровья и +0.02 к сопротивлению контролю
(потолок 0.6).

## Экипировка

Шесть слотов (ТЗ §7.3): `weapon`, `secondary`, `armor`, `boots` и два
украшения — `accessory_1`, `accessory_2`. Список живёт в
`GameState.EQUIPMENT_SLOTS` и он же единственная форма, которую принимает
`equip()`: слот из `data/items.json`, которого в этом списке нет, предмет
отказывается надевать вместо того, чтобы завести седьмой слот, который никто не
суммирует. В данных предмет называет слот `accessory` и попадает в первый
свободный из двух, а при занятых обоих заменяет `accessory_1`; надеть уже надетое
— no-op, поэтому одно кольцо не может занять оба слота и посчитаться дважды.
Надевание ничего не тратит: предмет остаётся в `inventory`, слот лишь помечает,
что он надет, поэтому любое надевание обратимо. Все суммы идут через
`GameState.total_bonus(stat)` — одну функцию, которая идёт по `EQUIPMENT_SLOTS` и
читает поле предмета; `total_attack()`, `total_defense()` и бонусы пересчёта — её
вызовы, поэтому задвоиться нечему. Сохранение, написанное пока слотов было два,
грузится без подъёма версии схемы: `_restore_equipment()` дописывает четыре
недостающих слота пустыми строками, ничего из уже надетого не теряется.

### Редкость и требования

Каждый предмет в `data/items.json` несёт `rarity` (пять уровней ТЗ §14.1:
`common`/`uncommon`/`rare`/`epic`/`legendary`), `icon` (одна юникод-глифа,
отрисовываемая стандартным шрифтом) и `source` — короткую строку о происхождении
(сундук, враг, торговец, ремесло). `ItemDB` отдаёт их через `rarity()`,
`icon()`, `source()` и `rarity_color()`: неизвестный уровень читается как
`common`, а цвет для него — отдельный, не совпадающий ни с одним уровнем, чтобы
опечатка в данных была видна, а не пряталась под общим белым. Цвет лишь
подкрепляет уровень и никогда его не заменяет: строка выбранной строки инвентаря
всегда проговаривает «Редкость: … · Источник: …» текстом.

Экипируемый предмет может требовать характеристики (`requires: {strength: 7}` и
т. п.). `GameState.equip()` перед надеванием сверяет каждое требование с
`attributes` и отказывает, если хоть одно не выполнено, — ничего не надевается и
инвентарь не трогается. `GameState.equip_blocker(item_id)` — единственный источник
правды об отказе: пустая строка значит «надеть можно», иначе это человекочитаемая
причина («Нужна сила 7 (у вас 5)»), и `equip()` спрашивает именно её, поэтому
HUD и сам гейт не могут разойтись. HUD показывает причину тостом вместо
размытого «нельзя», а под курсором — строку «Требуется: …» предупреждающим цветом.
Требование проверяется только в момент надевания: сохранение может держать
набор, который стартовые 5/5/5/5 уже не наденут, и это легально.

## Торговля

Торговец Йорек (`scripts/npcs/merchant.gd`, ставится в деревне)
открывает лавку. Данные лавки — `data/shop.json`: `merchant_id`, `buy_rate`
(доля цены покупки, возвращаемая при продаже) и список `stock` из пар
`item_id`/`amount` — сколько этого предмета торговец может продать. Запас
хранится в `ShopManager` и тратится при покупке; продажа в инвентаре запас **не
пополняет** — торговец не раздувает бесконечный оборот, скупая товар обратно.

`ShopManager` (`scripts/shop/shop_manager.gd`, `extends RefCounted`) — чистая
логика без UI и без обращений к автозагрузкам: конструктор принимает `GameState`
параметром, поэтому её можно создать и проверить в тесте без сцены. Цены берутся
из `data/items.json`: цена покупки — `price` предмета, цена продажи —
`maxi(0, floor(price * buy_rate))`, то есть продажа всегда невыгодна (купил за
20, продал за 10). Принудительного минимума в 1 нет: предмет с `price: 0` стоит
обратно 0, а `can_sell` отказывает ему причиной `no_value` («Нет цены») — иначе
бесплатный предмет стал бы бесконечным принтером золота.

Сделка атомарна (ТЗ §14.3): ни золото, ни предмет, ни запас не должны остаться
в полупозиции. `can_buy`/`can_sell` — чистые проверки без побочных эффектов,
`buy`/`sell` сначала вызывают их целиком, и только если всё в порядке, делают
необратимые шаги в единственном безопасном порядке. При покупке сначала
списывается золото (`spend_gold` — единственная операция, которая может
отказаться), затем добавляется предмет (`add_item`, с потолком стека
`MAX_STACK = 99`), и лишь потом убывает запас. При продаже сначала выдаётся
золото, затем убирается предмет; если убрать не удалось, начисление откатывается
обратным `add_gold` и сделка не считается состоявшейся. Отказ всегда
человекочитаемый и называется до изменения состояния: покупка — «неизвестный
предмет», «нет в запасе», «мало золота», «нет места»; продажа — «неизвестный
предмет», «нет в инвентаре», «квестовый предмет», «надетый предмет».

Лавка открывается не через сигнал `EventBus`, а напрямую: торговец находит HUD
по группе `hud` и зовёт `open_shop(shop)`, а `ShopPanel`
(`scripts/ui/shop_panel.gd`) рисует список, золото и причину отказа. Пока лавка
открыта, HUD перехватывает ввод (`Esc` закрыть, `Tab` переключает купля/продажа,
`↑↓` выбор, `E` купить/продать) и держит `ui_blocking`, чтобы игрок под открытой
лавкой не бил и не двигался. Первая встреча с Йореком и Браном сначала прогоняет их `yorek_intro`/`bran_intro` (последняя реплика выставляет `met_yorek`/`met_bran`), и лишь следующие интеракты открывают прилавок или верстак напрямую: раннер отказывает по `not_flag`, поэтому панель никогда не спрятана за уже услышанным приветствием.

## Ремесло

Ремесло (§14.4) устроено как торговля: данные отдельно, чистая логика отдельно,
тонкий UI. `data/recipes.json` — четыре рецепта по два на станцию (`herbalist`,
`smith`): зелья и постоянные улучшения снаряжения. Поле `station` говорит, кто
рецепт варит, `unlock_flag` — какой флаг `GameState` должен быть выставлен
(пустая строка значит «известен сразу»), `materials` — сколько и чего сгорит,
`gold` — пошлина, `upgrade` — постоянная прибавка к характеристике.

`CraftManager` (`scripts/craft/craft_manager.gd`, `extends RefCounted`) принимает
`GameState` параметром и опционально станцию: без станции он знает все рецепты,
с ней — только рецепты своей станции, поэтому кузнец не может сварить зелье.
`can_craft` — чистая проверка, `craft` сначала вызывает её целиком, а необратимые
шаги делает в единственном порядке: списать золото, убрать материалы, выдать
результат, наложить улучшение. Каждый последующий шаг имеет откат, хотя до него
дело не доходит: всё уже проверено. Порядок причин — часть контракта:
`unknown_recipe` → `locked` → `already_upgraded` → `not_enough_gold` →
`missing_material` → `no_space`, поэтому готовое улучшение отвечает «Это уже
улучшено», даже когда золота не осталось.

Постоянное улучшение живёт в `GameState.item_upgrades` (массив `{item_id,
stats}`), а не в предмете: `total_bonus()` прибавляет его на лету, так что
переэкипировка не может накрутить бонус второй раз. `apply_item_upgrade()`
атомарна и идемпотентна: если у предмета уже есть хоть одна характеристика из
блока, она не пишет ничего и возвращает `false`. Улучшение переживает
сохранение (`to_dict`/`from_dict`, `_restore_item_upgrades`) и не зависит от
того, лежит предмет в сумке или надет.

Станция — `Smith` (`scripts/npcs/smith.gd`, «Кузнец Бран»), тот же узор, что и
`Merchant`: ищет HUD по группе `hud`, зовёт `open_craft(craft_manager)`, а
`CraftPanel` (`scripts/ui/craft_panel.gd`) рисует список, золото, нужное/наличное
по материалам и строку результата с обещанием «Атака +2». Пока верстак открыт,
HUD перехватывает ввод (`Esc` закрыть, `↑↓` выбор, `E` создать) и держит
`ui_blocking`; верстак, лавка, карта, лист персонажа и экран навыков
исключают друг друга —
открытие одного закрывает другое. Кузнец ставится в точку генерируемой
карты, найденную `_find_walkable_away()`: она ищет проходимую клетку вокруг
якоря, но подальше от остальных NPC, чтобы путь бота до первого интерактивного
объекта не изменился. Травничество пока только в данных: травница Мила
(`Villager`) стоит в деревне и даёт задания, но станцию `herbalist` не открывает.

## Задания: одна цепочка

Двенадцать заданий в `data/quests.json` выстроены в одну линию, а не лежат
одинаково доступными с первого часа. Три поля на задание:

- `requires` — список заданий, которые обязаны быть сданы;
- `min_level` — минимальный уровень игрока (нужен ровно одному заданию);
- `next` — обратная ссылка, для проверки целостности линии.

Порядок: `q01_ash_wolves → q02_gather_fangs → q03_clear_boars → q09_the_mill →
q04_bone_guard → q05_ruin_key → q06_the_crown → q07_captain_guard →
q10_armor_fit → q08_the_bell → q11_light_the_way → q12_officers_seal`. У
`q10_armor_fit` стоит и `requires: ["q07_captain_guard"]`, и `min_level: 4`:
доспех должен быть и продолжением линии, и наградой за уровень, которого
игрок уже достиг собственными наградами основной линии — это проверяется
отдельно, без допущения о стороннем опыте.

`QuestManager` (`scripts/quests/quest_manager.gd`) добавляет пятое состояние —
`STATE_LOCKED := "locked"`. Оно **нигде не хранится**: `state_of()` выводит его
на лету из `requires`/`min_level`, поэтому в слоте не появляется состояния,
которое могло бы разъехаться с данными, и `to_dict`/`from_dict`/`reset`
остаются в прежней схеме. `locked` — единственное состояние, которого нет в
`data/quests.json`.

Вывод состояния выбран вместо явной выдачи по причине совместимости: `Npc`,
`Villager` и `QuestStone` сравнивают состояние со строками
`available`/`active`/`ready`/`done` и на незнакомую строку просто не реагируют,
так что закрытое задание не предложит никто из них, не изменившись ни строкой.
`start()` у закрытого задания отказывает с тостом и причиной
(`locked_reason()` — «Сначала нужно выполнить: …» либо «Нужен уровень N»),
и пишет событие `quest_start_refused`. Снятие блокировки пишется как событие
`quest_unlocked` и показывается тостом «Доступно задание: …» — игрок узнаёт о
новом задании, а не ищет его по деревне.

Отдельно закреплён дефект, из-за которого блокировка могла бы молча не работать:
`states.get(quest_id, {})` возвращает пустой `Dictionary`, который проходит
проверку `is Dictionary`, поэтому состояние всегда читалось как `available`.
Отправное значение — `null`, и тест проверяет именно отсутствие записи, а не
её пустоту.

Целостность линии проверяется как граф, а не перебором: одна вершина без
`requires` (голова), одна без `next` (хвост), рёбра `next` согласованы с
`requires`, обход от головы посещает все двенадцать, в свежей игре доступно
ровно одно задание и одиннадцать закрыты, а завершение головы открывает ровно
следующее звено и больше ничего. Взятое задание не отзывается, даже если
условие позже перестало выполняться, — отозвать у игрока уже начатую работу
хуже, чем показать задание на секунду раньше.

## Диалоги

Ветвящиеся диалоги (§12.2) следуют тому же узору, что торговля и ремесло:
данные отдельно, чистая логика отдельно, тонкий UI. `data/dialogue.json` —
реплики под ключом `dialogues`. У диалога есть `speaker_id` (к нему привязан
NPC), стартовая `start` и необязательное `condition` всего разговора. Узел
хранит `speaker`, `text`, необязательные `effects`, `next` (переход к другому
узлу) либо `options` — список вариантов, где каждый даёт `text`, свои
`effects` и `next`. Пустой `next` значит «конец».

`DialogueDB` (`scripts/dialogue/dialogue_db.gd`) — статическое ленивое хранилище
`data/dialogue.json`: читает файл один раз, отдаёт узлы и список разговоров по
`speaker_id`. Он не трогает `GameState` и синглтоны, поэтому вызывается по
`class_name` даже из `--script`, где автозагрузки ещё не зарегистрированы.

`DialogueRunner` (`scripts/dialogue/dialogue_runner.gd`, `extends RefCounted`)
принимает `GameState` и `QuestManager` параметрами в `__init` — как
`CraftManager` и `ShopManager`, — и потому тоже компилируется вне игрового
контекста. Он держит курсор разговора: `start` проверяет условие разговора,
`current_node`/`current_options` отдают текущее, `advance` ведёт по линейной
цепочке, `choose(index)` применяет эффекты варианта и переходит, возвращая
`{ok, next, effects}`. Эффекты узла применяются при входе на него, эффекты
варианта — при выборе. Условие понимает `quest_done`, `quest_active`, `flag`,
`not_flag`; эффект — выставить флаг или взять квест. Прочитанное помечается
ключом `"<dialogue_id>:<node_id>"` в `GameState.dialogue_read`, чтобы
повторный подход не показывал уже виденные реплики; набор переживает
сохранение (`to_dict`/`from_dict`, `_restore_dialogue_read`).

`Npc` (`scripts/npc/npc.gd`) несёт `speaker_id` и при `interact` собирает
`DialogueRunner.new(GameState, QuestManager)`, подбирая контекст: `intro` либо
`after_hunt` (когда задание уже взято или сдано). Если подходящего разговора
нет или его условие не выполнено, NPC возвращается к прежним репликам и
сдаче задания, поэтому старый путь ботов не ломается. HUD находит по группе
`hud` и зовёт `open_dialogue_runner(runner)`.

HUD рисует реплику, список вариантов с курсором `>` и живую строку подсказки;
пока открыт бегунок, он перехватывает ввод (`E` — реплика/выбор, `↑↓` —
вариант, `Tab` — автопоказ, `Space` — пропуск непрочитанного, `Esc` — закрыть)
и держит `ui_blocking`, останавливая время. Первый кадр ввода глушится, иначе
клавиша, открывшая диалог, тут же прокрутила бы узел.

`_migrate()` поднимает старые схемы; более новая схема не затирается, а

телеметрия, а не бот, поэтому прогон не выставляет себе оценку. Тест гоняет
`build_summary` на синтетическом входе и требует наличия каждого поля —
исчезнувшее поле не может остаться незамеченным.

## Отладочный бот

`scripts/debug_bot/bot.gd` — узел `Bot` в `main.tscn`, тринадцать сценариев
(`BOT-001`…`BOT-013`) и семь профилей. Единственная дверь в игру — подмена
источника ввода `InputSource.set_override(BotInput)`: бот не вызывает методы
игры и не пишет состояние, он нажимает кнопки. Отсюда архитектурное правило
всех новых сценариев: `PASS` обязан быть добыт поведением, а не авторством —
золото, HP и позиция игрока бот не меняет ни разу за прогон (закреплено
тестом `bot_extended` по исходнику тел сценариев).

Две вещи внутри бота заслуживают знания при правке мира:

- **походная механика** (`_travel_to`) — A* по логической сетке `cell_at()`
  плюс память физических столкновений (`_bumped`: упёрся дважды в одно место
  — тайл считается стеной; тайл цели в память не попадает; потолок 60 тайлов;
  перепланирование маршрута раз в 40 физ-кадров). Стоимость пути учитывает
  публичные группы `enemy` и `boss`: идти мимо врага дороже, мимо босса —
  вшестеро. У цены есть выключатель `avoid_threats`: он посчитан от того, где
  враги стоят *прямо сейчас*, поэтому длинную ногу через зону ведут без него —
  с включённой ценой маршрут пересобирается каждый раз, как скелет переступил,
  и нога из пяти тайлов съедала весь бюджет, мечась между двумя дорогами.
  Если логическая сетка и запечённая коллизия тайлов расходятся
  (известный случай: тайл (14,20) логически проходим, физически — невидимый
  угол), бот это лечит памятью столкновений; сама игра остаётся расходящейся,
  и это её дефект, а не обходной путь бота.
- **выход из задержания** (`_unstick`) — нога, две подряд не купившие даже
  восьми пикселей, удерживается не маршрутом: планировщик дорогу знает и
  продолжает по ней идти. Причина или в теле, вставшем в lane на дистанции,
  которую пороги ходка не покрывают (22 px для удара, а враг в 26 px — уже не
  цель и не стена), или в направлении обхода, одолженном три тайла назад и не
  забытом. Ответ один: отпустить клавиши, сбросить `_avoid_*` и `_bumped`,
  ударить ближайшего, если он рядом, и честно шагнуть на соседний тайл, с
  которого планировщик видит дорогу к цели ноги (а если цели нет — на тайл с
  самым большим открытым пространством за ним). Ни телепорта, ни лечения, ни
  записи в состояние. «Самое открытое место» без цели было причиной того, что
  один прогон десять минут пересекал один и тот же коридор: побег из кармана
  вёл обратно в карман, потому что вокруг кармана было больше свободного
  места.
- **зависание в модалке** — открытая панель для ходьбы выглядит местностью:
  пока `GameState.ui_blocking` поднят, герой не читает ввод вовсе, позиция
  повторяется до последней цифры, а план при этом каждый раз находит маршрут.
  `_travel_to` на зависании проверяет этот флаг и закрывает панель клавишей
  `pause` (второй тап — только если по-прежнему блокирует, чтобы случайно
  открытое меню паузы было тем же тапом снято); `interact` для этого не
  нажимается, потому что у прилавка он стоит игроку золота.
- **watchdog** (`_watchdog_tick`, включён на каждом прогоне) — три детектора
  ТЗ §19.6: встал (`WATCHDOG_STUCK_PX` за `WATCHDOG_STUCK_MS`), зациклился
  (`WATCHDOG_CYCLE_REPEATS` одинаковых действий), нулевой прогресс цели
  (`WATCHDOG_ZERO_PROGRESS_MS`). «Занимается делом» от «продвигается» отличает
  `_wd_progress_token`, собранный из публичных фактов мира, поэтому драка по
  кругу остановкой не считается. Срабатывание — запись доказательства в
  `decisions.jsonl` и счётчик `STUCK`; прогон watchdog не останавливает.
- **край нажатия** (`BotInput.is_action_just_pressed`) — отдаётся ровно один
  раз за физический тикд. Игрок опрашивает действие один раз за тикд, а вот
  обработчики HUD/лавки — дважды, и до фиксации края один тап покупал три
  зелья. Любой новый опрос `just_pressed` вне `_physics_process` теперь
  безопасен.

Профили читаются одним шлюзом `_pf(key, fallback)`: ключей старых четырёх
профилей в новых сценариях просто нет, и фолбэк воспроизводит прежнее
поведение байт-в-байт — поэтому расширение профилей не тронуло закрепленные
тестами `BOT-001/002/008/009/010/011`.

Единственная нога, где бот не пользуется панелью, — продажа в лавке:
переключатель режима панели читает `Tab` сырым клавиатурным опросом (для него
нет действия InputMap), недостижимым из `InputSource`; продажа идёт
`ShopManager.sell` — той же функцией, что вызывает обработчик `E` панели.
Ограничение зафиксировано в `BOT_GUIDE.md` §7.

### Зерно прогона

`PASS`, который нельзя повторить, — не проверка, а мнение. Пока зерно нигде не
записывалось, прогон нельзя было ни повторить, ни опровергнуть, поэтому зерно
теперь записывается, читается и печатается.

Порядок выбора (`Telemetry._apply_seed_from_cmdline()`):

1. `--seed=N` из командной строки (`seed_source = "cmdline"`);
2. иначе `BOT_DEFAULT_SEED = 20261122` для прогонов бота (`"bot_default"`);
3. иначе значение из часов (`"generated"`), чтобы обычная игра не играла двумя
   одними и теми же случайностями подряд.

Выбранное число уходит в `seed()` всего процесса, в `run_meta.json` полями
`seed`/`seed_source`, в событие `run_start` и в `summary.md`. Бот принимает
`--seed=` сам, передаёт его в `Telemetry.set_run_seed()` (то есть число,
названное оператором, действительно становится зерном процесса, а не
надписью), печатает его в строке вердикта и возвращает готовую команду повтора.

Отдельно пишется `world_seed` — зерно процедурной генерации. Оно не
дублируется: `Telemetry.world_seed()` читает `MAP_SEED` прямо со скрипта
`scripts/world/forest.gd` через `get_script_constant_map()`, поэтому вторая
константа не может молча разъехаться с первой после правки карты.

Чтобы зерно вообще на что-то влияло, из прогона убраны три источника
недетерминизма, не зависящие от него:

- окно soaka считается в физ-кадрах (`Engine.get_physics_frames() + soak_seconds
  × 60`), а не по `Time.get_ticks_msec()`: бюджет в 75 с, а тем более в 600 с,
  превращал вердикт в функцию загрузки машины. Дедлайны отдельных ног у других
  сценариев по-часам настенные, и это честная граница детерминизма: тот же флаг
  даёт тот же мир и тех же врагов, но не побайтово одинаковый лог;
- на время бота пул `AudioManager` паркуется (`_silence_audio_rng()` →
  `park_for_bot()`), потому что случайная высота тона в `play_sfx` тянет ту же
  глобальную последовательность, из которой игра берёт критический удар и добычу.
  Парковка заодно останавливает и выгружает каждый голос и снимает их с дерева —
  раньше `play_music` оставлял играющий плеер сиротой при очистке пула, и на
  выходе процесса `AudioStreamWAV`/`AudioStreamPlaybackWAV` светились утечкой;
- нажатие бота ставится на следующий физ-кадр, а не на тот, который увидел его
  корутин. Корутина возобновляется в idle-фазе между шагами, и кадр, который она
  читает, — то уже идущий шаг, то следующий; прежнее точное совпадение по кадру
  теряло нажатие, когда штамп и опрос игрока в `_physics_process` разъезжались на
  шаг, и одно зерно выдавало разное число атак от запуска к запуску. Цель —
  следующий шаг, поэтому доставка попадает в один недвусмысленный кадр независимо
  от того, где в кадре возобновилась корутина.

Замер: `--seed=777` даёт один и тот же вердикт пять прогонов из пяти,
`--seed=4242` — три из трёх, и эти два зерна дают разный результат
(`attacks=114` против `attacks=105`), что и доказывает: число используется по
назначению, а не просто печатается.

## Звук

`AudioManager` (`scripts/core/audio_manager.gd`) — единственный, кто знает про
звук. Геймплей его не вызывает: ни в одном скрипте, кроме самого
`audio_manager.gd`, имени `AudioManager` нет. Убираешь autoload — игра
замолкает, и ни одна механика от этого не ломается.

```
EventBus.damage_dealt ──> hit / hurt        (по группам цели)
EventBus.enemy_died   ──> enemy_die
EventBus.player_died  ──> hurt с pitch 0.6
EventBus.sfx_requested──> pickup, cast
GameState.ui_blocking ──> ui_click          (флаг открыт/закрыт)
группа "boss"          ──> boss_roar        (смена фазы)
```

**Шины** — `audio_bus_layout.tres`: `Master`, `Music`, `SFX`, `UI`; три
последние шлют в `Master`. Громкость живёт на шине, а не на плеере, поэтому
`set_volume()` слышно сразу, в том числе по звукам, которые уже играют.
`0.0` пишется как −80 dB, а не как `linear_to_db(0.0)` = −inf: бесконечность не
переживает запись в JSON.

**Пул** — 8 плееров на `SFX`, 2 на `UI`, 2 на `Music` (пара под кроссфейд) плюс
один отдельный плеер фонового эмбиента, все создаются в `_ready()`. Занятых всех
— берётся тот, кому отдали голос раньше всех, а не новый вызов в тишину: именно
поэтому частое комбо не режет само себя. Потоки читаются один раз и кэшируются,
в путях воспроизведения нет ни `await`, ни обращения к диску, ни
`Engine.time_scale`.

**Настройки** — `user://settings/audio.json`, отдельно от `user://saves/`
(ТЗ §18): слот сохранения хранит прогресс, а не предпочтения. Запись атомарная
(`.tmp` → проверка размером и парсингом → `rename`), битый файл оставляет
значения по умолчанию и сообщает об этом одной строкой без backtrace — того же
формата, что и `input_bindings.gd`. Меняются громкости в экране «Настройки»
(секция «Звук»): панель держит уровни как целые 0..100 только для текстовой
шкалы, а конвертацию в dB, клик и запись отдаёт `AudioManager` — сама она ни
одного плеера не создаёт и шину по имени не называет, находя автозагрузку через
`get_node_or_null` от корня сцены.

**Музыка и эмбиент.** Дорожки и фоновый эмбиент генерятся тем же
`tools/gen_audio.py` (см. `ASSET_CREDITS.md`). `play_music(name, fade)` крутит
петлю на шине `Music` и при смене дорожки ведёт кроссфейд по паре голосов:
входящая поднимается из −60 dB, исходящая уходит в −60 dB и останавливается,
`fade` по умолчанию 0,6 с; `fade = 0` режет мгновенно. Две дорожки одновременно
не звучат — тревел и смена на босса не могут наложить трек на трек.
`play_ambience(name)` — один фоновый слой на той же шине `Music`, но тише
музыки; один за раз, второй вызов заменяет первый. `current_music()` /
`current_ambience()` отдают текущее имя (пусто после остановки) — по ним
проверяется, что смена реально произошла.

Раскладка по сценам держится в самих сценах, а не в аудио: у зоны есть
виртуальные хуки `music_track()` и `ambience_track()` (пусто по умолчанию),
`zone_base._ready()` зовёт `_start_zone_audio()`, который и запускает дорожку
зоны. Бой с боссом перехватывает музыку со стороны HUD: пока жив босс, играет
`music_boss`, после победы/отступления возвращается дорожка зоны. Меню играет
`music_menu`. Победа глушит музыку и эмбиент и проигрывает `sting_victory` по
шине `SFX` — не по `Music`, чтобы не занять кроссфейдную пару. Поражение глушит
и музыку, и эмбиент, возврат из экрана поражения возвращает дорожку зоны.

Зацикливание включается в рантайме (`_enable_loop`): импортчик оставляет
`loop_end = 0`, что аудиосервер читает как нулевую область цикла, поэтому
`loop_mode = LOOP_FORWARD` сам по себе обрывает дорожку почти сразу; явный
`loop_end` по длине потока это чинит.

**Чего нет.** `step.wav` сгенерирован, но к событиям не подключён: шаговой
каденции игрока в срезе тоже нет.

**Почему два опроса, а не сигналы.** `GameState.ui_blocking` — обычная
переменная без сигнала, а `phase_changed` живёт на узле босса, которому про
звук знать не положено. Поэтому клик меню — это наблюдение за флагом, а смена
фазы — наблюдение за группой `boss`; оба стоят в одном `_process()` и в сценах
без босса второй цикл пустой. Компромисс осознанный: цена — два дешёвых опроса
кадр, выгода — ни одной строчки про звук в `scripts/ui/` и `scripts/ai/`.

## Меню и экраны

Загрузочная сцена — `scenes/main/menu.tscn` (`scripts/ui/main_menu.gd`), а не
`scenes/main/main.tscn`. Мир по-прежнему живёт своей сценой и ничего про меню не
знает: меню — это единственный узел, который знает про мир.

**Обход меню.** Меню — модальное окно перед игрой, а ботам, проверке сохранений и
скриншот-пробе нужен мир без этого окна. Поэтому `_ready()` первым делом спрашивает
`bypass_requested()` и, если просят, сразу уходит в `main.tscn`, не построив ни
одного контрола. Просят обход три вещи: любой аргумент командной строки с `--bot=`,
непустой `PEPEL_LOAD_SLOT` и непустой `PEPEL_SCREENSHOT`. Последнее — осознанное
исключение: скриншот-проба существует ровно для того, чтобы снять мир, и вешать на
неё меню значило бы сломать шесть уже написанных проверок. Для самого меню есть
отдельный переключатель `PEPEL_SCREENSHOT_UI=menu`, который обход отменяет.

**Передача загрузки.** Меню никогда не грузит зону само. Оно пишет номер слота в
`GameState.pending_load_slot`, а `main.gd::_apply_pending_load()` забирает его при
старте сцены — тем же кодом, которым всегда работал `PEPEL_LOAD_SLOT`. Пути загрузки
один, и у меню физически нет способа разойтись с ним: ни своего `load_game()`, ни
своей смены сцены с данными.

**«Новая игра»** сбрасывает `GameState` и доску заданий до того, как попросить мир,
и идёт по той же передаче, только со слотом 0.

**Экран поражения — не пауза.** `EventBus.player_died` открывает «Вы погибли», но
дерево не останавливается и `GameState.ui_blocking` не поднимается. Смерть уже
кому-то принадлежит: `_on_player_died()` в `player.gd` запускает анимацию и
`_dead_timer`, по которому `_respawn()` возвращает игрока на точку старта.
Остановить дерево здесь — значит посадить на этот таймер второго хозяина, и всё, что
экран ответить не может (бот затяжки, скриптовое воскрешение), останется мёртвым
навсегда: `BOT-010` на паузе ловил `hp=0` и 42 отступления там, где без паузы
проходит. `ui_blocking` тоже не поднят: мёртвый игрок в `State.DEAD` ввод не читает,
а этот экран забирает `_process()` у HUD раньше любой ветки панели — зато флаг
остановил бы на время анимации и часы суток, и расписания NPC, то есть менял бы мир,
а не экран. «Возродиться» ровно поэтому ничего не возрождает: оно убирает экран, а
свой таймер делает своё. Экран закрывается и по `player_respawned`, так что
воскрешение с любой стороны не оставит панель над живым игроком.

**Экран победы** — `show_victory(ending_id)`: три финала (`dawn`, `memory`, `crown`),
титры берутся у `MainMenu.credits_lines()` в одном месте, листаются стрелками.
Зовёт его `EndingAltar.choose()` — но не вхолостую: путь к нему один, через панель выбора
судьбы (`open_ending_choice`), которую открывает `interact()` у трона. Пока Король Без
Венца жив, ни панели, ни экрана нет; `memory` заперта без правды паломника, `crown` — без
правды и `rusted_seal`, снятого с Короля. Подтверждение на экране ведёт в главное
меню (`return_to_menu`), а не «закрыть»: в оконченный проходом мир возвращаться некуда.

**Из паузы в меню** — строка `Q — В главное меню` и отдельная обработка края
клавиши: панель паузы — список подсказок без курсора, поэтому выбор здесь не стрелки,
а одна клавиша. `return_to_menu()` перед сменой сцены гасит паузу, поражение, победу
и `ui_blocking`, а `_exit_tree()` HUD снимает паузу страховкой: сцена, приехавшая в
остановленное дерево с унаследованным `process_mode`, приехала бы замороженной, и
размораживать её было бы уже некому.

**Читаемость HUD (CRITIC-PLAYER).** Полосы HP/маны/XP и полоса опыта раньше висели
прямо на тайлах мира и терялись на светлых участках, а сам опыт был полосой в 3 px.
Теперь верхний блок (полосы) и нижняя полоса подсказок лежат на тёмных подложках
(`PLATE_COLOR`, `scripts/ui/hud.gd`) — плоских, почти непрозрачных, без рамки, чтобы
не рисовать жёсткую рамку поверх оверлея. Каждая полоса подписана числом
(`HP 42/100`, `MP 17/60`, `XP 30/120`), а не только цветной заливкой; полоса опыта
использует общую высоту `BAR_H` (7 px), а не принудительные 3. Подпись — контракт:
её формат проверяет тест группы `map`.

**Шрифт и его ограничение.** Пиксельного шрифта с кириллицей в локальных архивах
нет, а новый файл по правилам задачи скачивать нельзя. Это проверено, а не
предположено: пять шрифтов из `assets/assets4/` (`NormalFont.ttf`, `font8x8.png`,
`font24x30.png` из архива Ninja Adventure и `Kenney Future.ttf`,
`Kenney Future Narrow.ttf` из архива Kenney UI Pack) прогнаны через
`FontFile.set_data()` + `has_char()` — покрытие кириллицы у всех пяти **0 из 66**
требуемых кодовых точек; подробности и лицензии в `docs/ASSET_CREDITS.md`
(раздел «Шрифты»). Поставить любой из них означало бы заменить каждую русскую
строку на квадраты недостающих глифов, что хуже текущей ситуации.

Поэтому и HUD, и главное меню берут встроенный шрифт ОС. Раньше в обеих темах
были выключены сглаживание (`TextServer.FONT_ANTIALIASING_NONE`) и субпиксельное
позиционирование (`SUBPIXEL_POSITIONING_DISABLED`) — правка, которую попросил
CRITIC-P1-04 ради «пиксельного» текста. Работать она не могла: шрифт здесь
пропорциональный системный, а не пиксельный, и у глифов просто исчезали все
промежуточные тоны. Замер на закоммиченном кадре: вся строка заголовка меню
содержала **4** уровня серого (фон панели, чернила и два тона подложки) — то
есть бинарная 8-пиксельная растровая карта. Второй половиной причины был режим
растяжения: при `window/stretch/mode="viewport"` всё дерево `Control`
отрисовывалось в буфер 480×270 и растягивалось целым числом 3×, так что каждый
штрих оказывался кратен 3 пикселям окна без единого промежуточного значения.

Сейчас стоит `window/stretch/mode="canvas_items"` при прежнем
`scale_mode="integer"`: дерево `Control` по-прежнему размечается в логических
480×270, но растеризуется против реального окна 1440×810, потому что Godot
умножает кегль на масштаб холста — базовые 8 px растеризуются как 24 px, а
12 px на максимальном масштабе — как 36. В обеих темах включены серое
сглаживание (`FONT_ANTIALIASING_GRAY`) и автоматическое субпиксельное
позиционирование (`SUBPIXEL_POSITIONING_AUTO`); серое, а не LCD, потому что LCD
даёт цветные окаёмки, заметные поверх пиксель-арта. После правки та же строка
заголовка даёт **216** уровней серого вместо 4, из них 50 — на одной строке
развёртки; строка меню — 208 и 54. Чёткость держится не на отказе от
сглаживания, а на нативной плотности растеризации: это две разные настройки, и
путать их больше нельзя. Побочный эффект — захват кадра
(`get_viewport().get_texture()`) теперь отдаёт 1440×810, а не 480×270, то есть
скриншот показывает ровно то, что видит игрок.

Пиксель-арт остаётся жёстким по другой причине и проверяется отдельно:
`rendering/textures/canvas_textures/default_texture_filter=0` (nearest) плюс
целый масштаб холста. Проверка на кадре мира 1320×390: ни одного цвета,
которого нет хотя бы в одной из трёх фаз выравнивания исходной текстуры, —
значит, на границах тайлов линейной фильтрации нет; сканлайн через границу
травы и земли шагает по 3 пикселя окна и меняет цвет напрямую, без смеси.
Исключение честнее записывать, чем заметать: камера не прилипает к пиксельной
сетке, поэтому у нескольких строк спрайтов блок выходит 2 пикселя вместо 3 —
это дефект выравнивания камеры, а не размытие, и он был и до правки.

Меню строит свою `Theme` отдельно от HUD, и именно на этом дублировании
CRITIC-P1-04 уже закрывали лишь наполовину: правку внесли в `scripts/ui/hud.gd`,
а `scripts/ui/main_menu.gd` её не получил. Теперь обе темы проверяются тестом на
живом экземпляре (`theme_font` у HUD и `theme` у меню), так что разъехаться
незаметно они не могут. Полноценный пиксельный шрифт (с кириллицей) — отдельная
задача с выбором лицензии; это ограничение осознанное, а не недосмотр. Тема не
читает файл шрифта вообще, поэтому отсутствующий ассет не может её уронить —
падать просто негде. Размер базовой темы — 8 логических px, умноженный на
настройку «Размер шрифта» (100–150 %), округлённый до целого и зажатый в 8..12:
верхняя граница держит HUD внутри логических 480×270 на максимальном масштабе
(проверяет тест по `hud_content_bounds`), а целое значение нужно для предсказуемого
кегля, а не для «попадания в сетку» — сетку теперь даёт сам растер по окну.

**Настройки экрана реально что-то делают.** «Яркость вспышек» масштабирует тонировку
попадания и у игрока, и у врага: при 0 % вспышка — нейтральный множитель (`Color(1,1,1)`
для врага, `Color.WHITE` для игрока), то есть спрайт не меняется, но сам факт удара
не пропадает (таймер вспышки взводится и при нуле). «Дальтонизм» переводит цвета
редкости инвентаря на лестницу по светлоте, чтобы ранги различались не только тоном.
Всё это читается через autoload `Accessibility` по имени узла, поэтому игровой код не
называет его идентификатором и грузится даже под `godot --script`.

Венчающий босс святилища и три концовки теперь есть — см. раздел «Боссы» и трон
`EndingAltar`. Остальное не «сделано молча» — см. README.
