# Архитектура

## Поток данных

```
InputSource ──> Player / HUD
                   │
                   ├─> DamageResolver ──> HealthComponent / GameState
                   │                          │
                   │                          └─> EventBus (сигналы)
                   │                                   │
                   └─> Telemetry <─────────────────────┘
                          │
                          └─> user://debug_runs/<run_id>/
```

`EventBus` — единственный канал оповещения. Никто не держит прямых ссылок на
HUD, кроме сцены `main.tscn`.

## Autoload

| Имя | Файл | Ответственность |
| --- | --- | --- |
| `Telemetry` | `scripts/core/telemetry.gd` | Логи прогона, перехват ошибок движка |
| `EventBus` | `scripts/core/event_bus.gd` | Сигналы между системами |
| `GameState` | `scripts/core/game_state.gd` | HP/мана/XP/золото/инвентарь/флаги |
| `QuestManager` | `scripts/quests/quest_manager.gd` | Состояния квестов, выдача награды |
| `SaveManager` | `scripts/save/save_manager.gd` | Слоты, атомарная запись, миграции |
| `InputBindings` | `scripts/core/input_bindings.gd` | Переназначение клавиш, `user://settings/controls.json` |
| `HitStop` | `scripts/core/hit_stop.gd` | Общее замедление времени после удара, всегда возвращает `time_scale` к 1.0 |

Autoload'ов ровно семь: всё остальное — сцены и компоненты.

## Ввод

`InputSource` (`scripts/core/input_source.gd`) — статический фасад. Человек
читает `Input`, бот подменяет источник через `InputSource.set_override()`.
И игрок, и HUD опрашивают только `InputSource`, поэтому у бота нет
привилегированного доступа: он не может вызвать `queue_free` у врага или
прочитать его HP.

Экран «Настройки управления» (`scripts/ui/settings_panel.gd`, открывается из
паузы) читает сырые `InputEvent` — иначе перехватить произвольную клавишу
нельзя. Бот сырые события не порождает, поэтому переназначение для него
недостижимо, а правки `InputMap` на его прогоны не влияют. Назначения пишет
`InputBindings` в `user://settings/controls.json` — отдельно от слотов
сохранения (ТЗ §18).

Экран «Персонаж» (`scripts/ui/character_panel.gd`, открывается на C) — панель
характеристик, производных чисел и невложенных очков; опрашивает `InputSource`
через HUD, как остальные панели, и тратит очки только через
`GameState.spend_attribute_point()`.

## Бой

`DamageResolver.resolve_hit(attacker, target, payload)`:

1. отбрасывает повторный `hit_id` для той же цели;
2. считает крит, вычитает `get_defense()` цели;
3. вызывает `receive_damage()` у цели;
4. пишет событие в `combat.jsonl`.

Удар игрока: `WINDUP 0.08 → ACTIVE 0.10 → RECOVERY 0.16`. Хитбокс открывается
только в ACTIVE, `hit_id` создаётся один раз на замах.

### Комбо

Цепочка ударов (ТЗ §6 «Комбо зависят от оружия») живёт на `Player`, а все её
параметры берутся из данных надетого оружия — `ItemDB.combo_steps()` и
`ItemDB.combo_window()`. Шаг цепочки: `damage_mult`, `windup`, `active`,
`recovery`, `reach` (множитель выноса хитбокса) и `arc` (множитель его размера).
`iron_sword` — 3 быстрых шага, `iron_spear` — 2 медленных, но с бо́льшим
вылетом.

Новое оружие кода не требует: достаточно положить `combo` в `data/items.json`.
Оружия без `combo` (и кулаки) бьют одиночным замахом из констант `Player`,
поэтому ничего не регрессирует.

Порядок такой: шаг выбирается в момент старта замаха, а после его окончания
открывается окно комбо (`combo_window` секунд). Следующая атака внутри окна
переводит цепочку на следующий шаг, после последнего шага — по кругу на первый.
Окно протекло — цепочка обнуляется, и следующий удар снова первый шаг. Окно
тикает только вне замаха: у копья шаг (0.66 с) дольше собственного окна (0.55 с),
и иначе цепочка обрывалась бы под ударом, который ещё идёт.

### Статусы

`StatusComponent` (`scripts/combat/status_component.gd`) — переиспользуемый узел
эффектов (ТЗ §8.2). Навешивается кодом на `Enemy` и `Player` (не через `.tscn`).
Шесть статусов: `burn` (горение, периодический урон), `chill` (холод, замедление
до 0.6), `shock` (разряд, блокирует действия), `root` (корни, блокирует
движение), `blight` (порча, периодический урон и лечение ×0.5), `stun`
(оглушение, блокирует действия и движение).

Любое будущее заклинание получает статусы бесплатно: достаточно положить в
payload `DamageResolver.resolve_hit` ключи `status` и `status_duration` —
резолвер вызовет `apply_status()` у дочернего `StatusComponent` цели.
Сопротивление цель отдаёт через метод `get_status_resistance(status)` (0..1);
полное сопротивление (1.0) отклоняет статус. `burn`/`blight`/`chill`/`root`
складываются (до 5 стаков) и обновляются до большей длительности; `shock`/`stun`
не стакаются, только обновляют длительность. Периодический урон (`burn` 3,
`blight` 2 за тик, умноженно на стаки) идёт обратно через `DamageResolver`, а не
напрямую, поэтому подчиняется тем же правилам дедупликации, защиты и телеметрии.

## Комбинации

`Combinations` (`scripts/combat/combinations.gd`) — единственная таблица
элементальных взаимодействий (ТЗ §9.2). Правил четыре:

| Комбинация | Что происходит |
| --- | --- |
| лёд + физика | по замороженной цели физический удар выбивает более глубокий стаггер (+0.25 с); урон не меняется |
| огонь + корни | корни сгорают, остаётся маркер дыма (`SmokeZone`, 3 с); урона нет никакого |
| молния + мокрая цель | `shock` по цели с `chill` бьёт по ближайшим врагам в 70 px, не больше `MAX_CHAIN_TARGETS` (3), уроком вдвое меньше исходного |
| лечение + порча | лечение сгорает по одному стеку `blight` и проходит с множителем 0.5 |

Единая точка входа: `DamageResolver.resolve_hit` вызывает
`Combinations.on_hit()` до передачи результата в `receive_damage()` (иначе цель
не успеет прочитать блок `combination`) и `Combinations.on_status_applied()`
сразу после успешного `apply_status()`. Лечение идёт через
`Player.heal_with_status` → `Combinations.on_heal()`. Ни один атакующий, ни один
статус, ни один навык своего правило не реализует.

Защита от рекурсии: цепная молния резолвится с флагом `no_chain: true` и без
ключа `status`, поэтому второй уровень не возникает даже теоретически;
дополнительно счётчик `_chain_depth` и потолок `MAX_SMOKE_ZONES` держат под
контролём и глубину, и число маркеров. `on_hit()` не наносит урона вообще, так
что ни одно правило не может породить новый `resolve_hit` из `receive_damage()`.
Мёртвая цель не реагирует ни на одно правило, а удар, оказавшийся смертельным,
теряет блок `combination`.

## Враги

`Enemy` (`scripts/ai/enemy.gd`) — явная FSM с таймером состояния. Телеграф —
`ColorRect`, который проявляется во время WINDUP; хитбокс открывается после.
Дальний враг стреляет снарядом (`Projectile`), урон всё равно идёт через
`DamageResolver`. Отличия конкретного типа задаются не новым скриптом, а
экспортами `Enemy` — `speed_multiplier`, `attack_cooldown_multiplier`,
`windup_multiplier`, `charge_on_sight` (полуторная дальность обнаружения и
отказ от минимальной дистанции удержания) и `sprite_tint`; у всех них нейтральное
значение (1.0 / false / белый), поэтому волк и культист играют ровно так же, как
до появления этих параметров.

### Боссы

`Boss` (`scripts/ai/boss.gd`) наследуется от `Enemy` и не дублирует FSM: весь
цикл состояний, телеграф, хитбоксы и `DamageResolver` остаются базовыми, а босс
подменяет ровно три точки. `phase_two_health_fraction` (по умолчанию 0.5) —
порог ярости, он считается один раз от `max_health` и в фазу 2 возвращается
только через `_phase >= 2`, поэтому откат лечения назад фазу не меняет; при
переходе босс добавляет себе `enraged_speed_multiplier` и
`enraged_cooldown_multiplier` поверх уже выставленных в сцене множителей типа.
Тяжёлый замах — это счётчик: `_swing_counter % HEAVY_SWING_EVERY == 0`, то есть
каждый третий, а не случайность и не таймер; множители урона и замаха берутся из
констант, а `windup_multiplier` базового класса одалживается на один замах и
обязательно возвращается, когда состояние ATTACK заканчивается, — иначе следующий
обычный замах остался бы медленным. Стаггер закрыт переопределением `_enter()`:
базовый `receive_damage()` сначала пишет `_stagger_bonus` из блока `combination`
пришедшего удара и только потом просит STAGGER, так что «обычный удар не сбивает,
связка лёд+физика сбивает» — это проверка `_stagger_bonus > 0.0`, а не отдельный
список типов урона.

Хранитель леса (`scenes/enemies/forest_warden.tscn`) — первый босс: 180 hp,
16 урона, коробочка тела больше волчьей (18x14 против 12x10), `speed_multiplier`
0.85, награда 120 xp / 60 золота и `echo_amulet` со 100% шансом. Ставится в
`forest.gd` последним спавном у дальней восточной стены: боты (BOT-008, BOT-010)
ищут цель в радиусе заведомо меньше `LEASH_RADIUS` босса, поэтому разнести босса
по отдельной ветке проверки не требуется.

Полоса босса берёт цель не из сигнала, а из группы `boss`: `Hud` раз в кадр
смотрит `get_first_node_in_group("boss")` и держит панель, пока игрок внутри
`BOSS_ENGAGE_RADIUS` (200 px) и босс жив. Группа вместо ссылки — чтобы `Hud` не
зависел от того, какой мир сейчас собран и сколько в нём боссов. Живость
проверяется по `HealthComponent.is_dead`, а не по наличию узла: труп гаснет
0.45 с через `Tween` и всё это время висит в дереве, так что одной проверки на
`null` хватило бы, чтобы полоса пережила собственного босса.

## Мир

`Forest` (`scripts/world/forest.gd`) собирает карту из детерминированного сида:
`TileSet` создаётся в рантайме, у камня и дерева есть коллизия. Спавны описаны
в одном месте, координаты в тайлах.

### Время суток и расписания

`DayClock` (`scripts/world/day_clock.gd`) — дочерний узел `Forest`, не autoload;
мир-срез владеет им сам. Хранит `time_fraction` от 0 до 1, за кадр продвигает
его на `delta / day_length_seconds` и на смене порога шлёт `phase_changed`.
Такты стоят, пока стоит игра или пока открыт любой интерфейс
(`GameState.ui_blocking`), — во время диалога или меню время не идёт. Фазы и
их начала берутся из `data/schedules.json`, а не зашиты в код.

`ScheduleComponent` (`scripts/npc/schedule_component.gd`) вешается на Эдрика,
Йорика и Брана и по `phase_changed` ведёт носителя на тайл текущей фазы.
Тайл берётся из `schedules.json`, но перед каждым шагом проверяется через
`Forest.cell_at`: шаг делается только по проходимой клетке, поэтому NPC не
заходит в стену и не зависает. Если дойти не выходит (тайл занят или недостижим
за `WALK_TIMEOUT`), носитель телепортируется в ближайшую проходимую клетку
расписания. Носители остаются `Area2D` со `collision_mask = 0`, так что
расписание не создаёт новых физических блокировок проходов.

`data/schedules.json` — единственное место, где правят расписание: `phases`
(4 фазы с `start` от 0 до 1), `npcs` (имя → тайл на фазу),
`day_length_seconds`. HUD рисует строку часов (`Утро · 06:00`) не чаще раза
в секунду; `refresh_clock_line()` вызывается напрямую из теста и скриншот-
пробы, чтобы проверка не зависела от троттла.

## Характеристики

Четыре характеристики (ТЗ §7.1) — Сила, Ловкость, Интеллект, Выносливость — по
5 очков на старте, потолок 30 на характеристику (`MAX_ATTRIBUTE`: без него одну
ветку можно было бы качать до выхода производного числа за пределы играбельного),
2 очка за уровень, потолок уровня 20. Кривая опыта и все коэффициенты лежат в
`data/progression.json`, где `xp_curve[n]` — сколько опыта нужно суммарно на
уровень `n+1`, поэтому настройка прогрессии не трогает код. Единственная точка,
где характеристики превращаются в числа, — `GameState.recompute_derived()`: она
только присваивает (`база + рост уровня + очки характеристики`) и никогда ничего
не прибавляет, поэтому повторный вызов даёт ровно те же числа, а текущие `hp` и
`mana` лишь подтягиваются под новые максимумы. Экипировка входит в пересчёт
только бонусами скорости и сопротивления (`speed_bonus`, `resist_bonus`), и тоже
через присваивание: `total_bonus()` каждый раз заново суммирует надетое по всем
шести слотам, поэтому снятие вещи не оставляет следа. Атака и защита не
кэшируются и читаются там, где используются (`total_attack()`,
`total_defense()`, `Player._magic_damage()`), временные эффекты в пересчёт не
входят вовсе. Сила даёт +1 к атаке за очко,
Ловкость — +0.005 к шансу крита и +0.8% к скорости (потолок 1.3), Интеллект — +4
к максимуму маны и +0.06 к множителю магического урона (пол 1.0, потолок 2.5),
Выносливость — +5 к максимуму здоровья и +0.02 к сопротивлению контролю
(потолок 0.6).

## Экипировка

Шесть слотов (ТЗ §7.3): `weapon`, `secondary`, `armor`, `boots` и два
украшения — `accessory_1`, `accessory_2`. Список живёт в
`GameState.EQUIPMENT_SLOTS` и он же единственная форма, которую принимает
`equip()`: слот из `data/items.json`, которого в этом списке нет, предмет
отказывается надевать вместо того, чтобы завести седьмой слот, который никто не
суммирует. В данных предмет называет слот `accessory` и попадает в первый
свободный из двух, а при занятых обоих заменяет `accessory_1`; надеть уже надетое
— no-op, поэтому одно кольцо не может занять оба слота и посчитаться дважды.
Надевание ничего не тратит: предмет остаётся в `inventory`, слот лишь помечает,
что он надет, поэтому любое надевание обратимо. Все суммы идут через
`GameState.total_bonus(stat)` — одну функцию, которая идёт по `EQUIPMENT_SLOTS` и
читает поле предмета; `total_attack()`, `total_defense()` и бонусы пересчёта — её
вызовы, поэтому задвоиться нечему. Сохранение, написанное пока слотов было два,
грузится без подъёма версии схемы: `_restore_equipment()` дописывает четыре
недостающих слота пустыми строками, ничего из уже надетого не теряется.

### Редкость и требования

Каждый предмет в `data/items.json` несёт `rarity` (пять уровней ТЗ §14.1:
`common`/`uncommon`/`rare`/`epic`/`legendary`), `icon` (одна юникод-глифа,
отрисовываемая стандартным шрифтом) и `source` — короткую строку о происхождении
(сундук, враг, торговец, ремесло). `ItemDB` отдаёт их через `rarity()`,
`icon()`, `source()` и `rarity_color()`: неизвестный уровень читается как
`common`, а цвет для него — отдельный, не совпадающий ни с одним уровнем, чтобы
опечатка в данных была видна, а не пряталась под общим белым. Цвет лишь
подкрепляет уровень и никогда его не заменяет: строка выбранной строки инвентаря
всегда проговаривает «Редкость: … · Источник: …» текстом.

Экипируемый предмет может требовать характеристики (`requires: {strength: 7}` и
т. п.). `GameState.equip()` перед надеванием сверяет каждое требование с
`attributes` и отказывает, если хоть одно не выполнено, — ничего не надевается и
инвентарь не трогается. `GameState.equip_blocker(item_id)` — единственный источник
правды об отказе: пустая строка значит «надеть можно», иначе это человекочитаемая
причина («Нужна сила 7 (у вас 5)»), и `equip()` спрашивает именно её, поэтому
HUD и сам гейт не могут разойтись. HUD показывает причину тостом вместо
размытого «нельзя», а под курсором — строку «Требуется: …» предупреждающим цветом.
Требование проверяется только в момент надевания: сохранение может держать
набор, который стартовые 5/5/5/5 уже не наденут, и это легально.

## Торговля

Торговец Йорик (`scripts/npcs/merchant.gd`, ставится в деревне на опушке)
открывает лавку. Данные лавки — `data/shop.json`: `merchant_id`, `buy_rate`
(доля цены покупки, возвращаемая при продаже) и список `stock` из пар
`item_id`/`amount` — сколько этого предмета торговец может продать. Запас
хранится в `ShopManager` и тратится при покупке; продажа в инвентаре запас **не
пополняет** — торговец не раздувает бесконечный оборот, скупая товар обратно.

`ShopManager` (`scripts/shop/shop_manager.gd`, `extends RefCounted`) — чистая
логика без UI и без обращений к автозагрузкам: конструктор принимает `GameState`
параметром, поэтому её можно создать и проверить в тесте без сцены. Цены берутся
из `data/items.json`: цена покупки — `price` предмета, цена продажи —
`maxi(0, floor(price * buy_rate))`, то есть продажа всегда невыгодна (купил за
20, продал за 10). Принудительного минимума в 1 нет: предмет с `price: 0` стоит
обратно 0, а `can_sell` отказывает ему причиной `no_value` («Нет цены») — иначе
бесплатный предмет стал бы бесконечным принтером золота.

Сделка атомарна (ТЗ §14.3): ни золото, ни предмет, ни запас не должны остаться
в полупозиции. `can_buy`/`can_sell` — чистые проверки без побочных эффектов,
`buy`/`sell` сначала вызывают их целиком, и только если всё в порядке, делают
необратимые шаги в единственном безопасном порядке. При покупке сначала
списывается золото (`spend_gold` — единственная операция, которая может
отказаться), затем добавляется предмет (`add_item`, с потолком стека
`MAX_STACK = 99`), и лишь потом убывает запас. При продаже сначала выдаётся
золото, затем убирается предмет; если убрать не удалось, начисление откатывается
обратным `add_gold` и сделка не считается состоявшейся. Отказ всегда
человекочитаемый и называется до изменения состояния: покупка — «неизвестный
предмет», «нет в запасе», «мало золота», «нет места»; продажа — «неизвестный
предмет», «нет в инвентаре», «квестовый предмет», «надетый предмет».

Лавка открывается не через сигнал `EventBus`, а напрямую: торговец находит HUD
по группе `hud` и зовёт `open_shop(shop)`, а `ShopPanel`
(`scripts/ui/shop_panel.gd`) рисует список, золото и причину отказа. Пока лавка
открыта, HUD перехватывает ввод (`Esc` закрыть, `Tab` переключает купля/продажа,
`↑↓` выбор, `E` купить/продать) и держит `ui_blocking`, чтобы игрок под открытой
лавкой не бил и не двигался.

## Ремесло

Ремесло (§14.4) устроено как торговля: данные отдельно, чистая логика отдельно,
тонкий UI. `data/recipes.json` — четыре рецепта по два на станцию (`herbalist`,
`smith`): зелья и постоянные улучшения снаряжения. Поле `station` говорит, кто
рецепт варит, `unlock_flag` — какой флаг `GameState` должен быть выставлен
(пустая строка значит «известен сразу»), `materials` — сколько и чего сгорит,
`gold` — пошлина, `upgrade` — постоянная прибавка к характеристике.

`CraftManager` (`scripts/craft/craft_manager.gd`, `extends RefCounted`) принимает
`GameState` параметром и опционально станцию: без станции он знает все рецепты,
с ней — только рецепты своей станции, поэтому кузнец не может сварить зелье.
`can_craft` — чистая проверка, `craft` сначала вызывает её целиком, а необратимые
шаги делает в единственном порядке: списать золото, убрать материалы, выдать
результат, наложить улучшение. Каждый последующий шаг имеет откат, хотя до него
дело не доходит: всё уже проверено. Порядок причин — часть контракта:
`unknown_recipe` → `locked` → `already_upgraded` → `not_enough_gold` →
`missing_material` → `no_space`, поэтому готовое улучшение отвечает «Это уже
улучшено», даже когда золота не осталось.

Постоянное улучшение живёт в `GameState.item_upgrades` (массив `{item_id,
stats}`), а не в предмете: `total_bonus()` прибавляет его на лету, так что
переэкипировка не может накрутить бонус второй раз. `apply_item_upgrade()`
атомарна и идемпотентна: если у предмета уже есть хоть одна характеристика из
блока, она не пишет ничего и возвращает `false`. Улучшение переживает
сохранение (`to_dict`/`from_dict`, `_restore_item_upgrades`) и не зависит от
того, лежит предмет в сумке или надет.

Станция — `Smith` (`scripts/npcs/smith.gd`, «Кузнец Бран»), тот же узор, что и
`Merchant`: ищет HUD по группе `hud`, зовёт `open_craft(craft_manager)`, а
`CraftPanel` (`scripts/ui/craft_panel.gd`) рисует список, золото, нужное/наличное
по материалам и строку результата с обещанием «Атака +2». Пока верстак открыт,
HUD перехватывает ввод (`Esc` закрыть, `↑↓` выбор, `E` создать) и держит
`ui_blocking`; верстак, лавка, карта и лист персонажа исключают друг друга —
открытие одного закрывает другое. Кузнец ставится в точку генерируемой
карты, найденную `_find_walkable_away()`: она ищет проходимую клетку вокруг
якоря, но подальше от остальных NPC, чтобы путь бота до первого интерактивного
объекта не изменился. Травничество пока только в данных — своего NPC в лесу нет.

## Диалоги

Ветвящиеся диалоги (§12.2) следуют тому же узору, что торговля и ремесло:
данные отдельно, чистая логика отдельно, тонкий UI. `data/dialogue.json` —
реплики под ключом `dialogues`. У диалога есть `speaker_id` (к нему привязан
NPC), стартовая `start` и необязательное `condition` всего разговора. Узел
хранит `speaker`, `text`, необязательные `effects`, `next` (переход к другому
узлу) либо `options` — список вариантов, где каждый даёт `text`, свои
`effects` и `next`. Пустой `next` значит «конец».

`DialogueDB` (`scripts/dialogue/dialogue_db.gd`) — статическое ленивое хранилище
`data/dialogue.json`: читает файл один раз, отдаёт узлы и список разговоров по
`speaker_id`. Он не трогает `GameState` и синглтоны, поэтому вызывается по
`class_name` даже из `--script`, где автозагрузки ещё не зарегистрированы.

`DialogueRunner` (`scripts/dialogue/dialogue_runner.gd`, `extends RefCounted`)
принимает `GameState` и `QuestManager` параметрами в `__init` — как
`CraftManager` и `ShopManager`, — и потому тоже компилируется вне игрового
контекста. Он держит курсор разговора: `start` проверяет условие разговора,
`current_node`/`current_options` отдают текущее, `advance` ведёт по линейной
цепочке, `choose(index)` применяет эффекты варианта и переходит, возвращая
`{ok, next, effects}`. Эффекты узла применяются при входе на него, эффекты
варианта — при выборе. Условие понимает `quest_done`, `quest_active`, `flag`,
`not_flag`; эффект — выставить флаг или взять квест. Прочитанное помечается
ключом `"<dialogue_id>:<node_id>"` в `GameState.dialogue_read`, чтобы
повторный подход не показывал уже виденные реплики; набор переживает
сохранение (`to_dict`/`from_dict`, `_restore_dialogue_read`).

`Npc` (`scripts/npc/npc.gd`) несёт `speaker_id` и при `interact` собирает
`DialogueRunner.new(GameState, QuestManager)`, подбирая контекст: `intro` либо
`after_hunt` (когда задание уже взято или сдано). Если подходящего разговора
нет или его условие не выполнено, NPC возвращается к прежним репликам и
сдаче задания, поэтому старый путь ботов не ломается. HUD находит по группе
`hud` и зовёт `open_dialogue_runner(runner)`.

HUD рисует реплику, список вариантов с курсором `>` и живую строку подсказки;
пока открыт бегунок, он перехватывает ввод (`E` — реплика/выбор, `↑↓` —
вариант, `Tab` — автопоказ, `Space` — пропуск непрочитанного, `Esc` — закрыть)
и держит `ui_blocking`, останавливая время. Первый кадр ввода глушится, иначе
клавиша, открывшая диалог, тут же прокрутила бы узел.

## Сохранения

```
user://saves/slot_N.tmp     запись
       ↓ проверка размера и парсинг
user://saves/slot_N.bak     предыдущий хороший слот
user://saves/slot_N.json    актуальный слот
```

`_migrate()` поднимает старые схемы; более новая схема не затирается, а
отклоняется с понятной ошибкой.

## Логи

`user://debug_runs/<run_id>/`

| Файл | Содержимое |
| --- | --- |
| `run_meta.json` | версия движка, платформа, время старта |
| `events.jsonl` | все игровые события |
