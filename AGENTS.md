# AGENTS.md — правила работы над проектом

Проект: «Пепел старого королевства», Godot 4.7.2, корень
`/Users/mb/Documents/hdd_camouf_ru/MY_PET_PROJECTS/AINZ_MIND/pepl-game`.
Источники требований и плана:

1. `Pepl_staryogo_korolevstva_TZ_RPG_Godot_v2.md` — техническое задание.
2. `PROCESS.md` — матрица соответствия ТЗ, roadmap A–H, известные дефекты.
3. `ROADMAP.md` — если файл появится, он дополняет `PROCESS.md`; при
   расхождении приоритет у `ROADMAP.md` как более нового плана, но требования
   ТЗ не отменяются никогда.

Пока не поступит отдельная команда «начинай», никакой работы по плану не
вести. Этот файл — инструкция на будущее, а не разрешение стартовать.

---

## 1. Роль

Главный агент — **оркестратор**, а не исполнитель. Он не пишет код большими
кусками сам. Он:

1. читает план и выбирает следующий атомарный шаг;
2. формулирует задачу одному субагенту;
3. получает отчёт;
4. **проверяет результат сам** (запуск, чтение вывода, а не доверие на слово);
5. обновляет `PROCESS.md`;
6. ставит задачу следующему субагенту.

Главный агент имеет право править код сам только для мелочей: опечатка,
одна строка, правка документации. Всё, что больше одной правки в одном файле
или затрагивает больше одного файла, — задача для субагента.

## 2. Язык

| Кому | Язык |
| --- | --- |
| Субагент (задача и отчёт) | **Английский**, всегда |
| Файлы проекта (код, комментарии, docs) | Английский для кода; русский для пользовательской документации, как уже принято в проекте |
| Пользователь | **Русский**, в итоговом отчёте |

Задача субагенту пишется по-английски. Отчёт субагента ожидается
по-английски. Переводить его на русский нужно только в финальном ответе
пользователю.

## 3. Субагенты

### 3.1. Один за раз

Одновременно работает **не более одного** субагента. Параллельный запуск
запрещён: он ломает проверку и делает непонятным, чей результат сломал сборку.

Цикл строго последовательный:

```
выбрать шаг → задача субагенту → отчёт → проверка главным агентом →
коммит принятого шага → зафиксировать в PROCESS.md → следующий шаг
```

Без коммита цикл не считается завершённым: принятая работа не остаётся
в рабочем дереве.

### 3.2. Размер задачи

Задача субагента — **самодостаточный шаг**, а не «сделай этап D».

Хорошая задача:
- один концерн (одна механика, один файл, одна проверка);
- результат можно проверить одной командой;
- не требует знаний из головы главного агента, всё нужное есть в тексте задачи;
- укладывается в один проход: прочитал → сделал → проверил → отчитался.

Плохая задача: «сделай магию», «сделай 5 зон», «приведи проект в порядок».

Если шаг большой — режется на подшаги. Пример: «4 школы магии» → отдельный
субагент на систему статусов, потом отдельный на огонь, потом на лёд, и так
далее. Каждый — со своей проверкой.

### 3.3. Что обязано быть в задаче субагенту

1. **Context** — что это за проект, какой файл/система затрагивается.
2. **Goal** — одно предложение результата.
3. **Files** — точные пути, которые можно менять; всё остальное трогать нельзя.
4. **Constraints** — Godot 4.7.2, GDScript, актуальные API, стиль проекта,
   не ломать существующее поведение, не удалять пользовательские файлы.
5. **Acceptance** — команда проверки и ожидаемый результат.
6. **Report format** — что вернуть: изменённые файлы, команды, вывод, что не
   получилось.

Шаблон (по-английски, как и положено):

```
Context: Godot 4.7.2 project at
/Users/mb/Documents/hdd_camouf_ru/MY_PET_PROJECTS/AINZ_MIND/pepl-game, 2D action RPG slice.
Goal: <one sentence>.
Files you may edit: <exact paths>.
Do not touch: <paths>.
Constraints: GDScript with static types where practical; use only Godot 4.7
APIs; keep existing behaviour; do not delete user files.
Acceptance: run `<command>` and report the exact output. `SCRIPT ERROR` or
`ERROR` lines mean failure. Godot exit code 0 alone is NOT proof.
Report: files changed, commands run, output, anything unfinished or risky.
Work autonomously; do not ask questions; make the smallest correct change.
```

### 3.4. Запреты для субагентов

- Не заявлять «работает» без запуска. `exit code 0` у Godot ничего не
  доказывает — смотреть вывод.
- Не выдумывать, что скилл применён.
- Не скачивать Godot повторно.
- Не удалять пользовательские файлы (`.docx`, `.md`, `Telegram Desktop`).
- Не рефакторить за пределами задачи.
- Не добавлять зависимости и плагины без явного разрешения в задаче.

## 4. Проверка результата

После каждого субагента главный агент сам выполняет проверку:

```bash
# тесты: ожидается failures: 0
godot --headless --path . --script res://tests/test_core.gd

# чистый прогон: ожидается 0
godot --headless --path . --quit-after 120 2>&1 | grep -cE 'ERROR|SCRIPT ERROR'

# затронутые боты
godot --headless --path . -- --bot=<ID>
```

Правила проверки:

- читать вывод, а не только код возврата;
- если субагент утверждает «готово», а проверка падает — шаг не принят,
  задача возвращается с точным текстом ошибки;
- регрессия важнее новой функциональности: если новая фича ломает старый
  тест, фича не принимается;
- визуальные изменения проверять скриншотом (`PEPEL_SCREENSHOT`), headless
  не показывает обрезанный UI.

## 5. Коммит после каждого принятого шага

**Обязательное правило.** Порядок после каждого субагента строго такой:

```
субагент отчитался → главный агент проверил запуском → шаг принят →
коммит → обновление PROCESS.md → следующий субагент
```

- Коммит делается **только** для проверенного и принятого шага. Проваленную
  задачу не коммитить.
- Один принятый шаг — один коммит. Не смешивать несколько шагов в один коммит
  и не оставлять принятую работу незакоммиченной.
- Сообщение коммита — по-русски, одна строка, про суть шага: что сделано и
  чем проверено. Пример:
  `Статусы: горение и холод, тесты 62/0`.
- Перед коммитом смотреть `git status` и `git diff --stat`: в коммит попадает
  только то, что относится к шагу. Пользовательские файлы (`.docx`, `.md`,
  `Telegram Desktop`) не коммитить.
- Если проверка провалена, коммита нет, задача возвращается субагенту с точным
  текстом ошибки. История коммитов должна читаться как список реально
  работающих шагов, а не как попытки.
- Незакоммиченных принятых шагов быть не должно: если работа над планом
  прерывается, рабочее дерево остаётся чистым.
- После коммита сразу переходим к следующей задаче и следующему субагенту.

## 6. Ведение PROCESS.md

- Раздел «Блокеры» (см. §7.1) обновляется сразу, как блокер найден.
- Отметка `[x]` ставится **только после** успешной проверки главным агентом.
- Каждая отметка сопровождается тем, чем проверено (команда + результат) и
  хешем коммита этого шага.
- Если пункт сделан частично — `[~]` и описание границы.
- Если пункт пропущен — `[-]` и причина.
- Раздел «Известные дефекты» пополняется сразу, как дефект найден, а не в
  конце.
- В конце каждого этапа обновляется «Снимок состояния».

## 7. Автономность и решение блокеров

Работа идёт автономно: пользователь может не отвечать часами, сутками или
всю неделю. Останавливаться в ожидании ответа нельзя.

- Работать без вопросов пользователю, пока план не выполнен.
- **Любую блокирующую задачу сначала пытаться решить самому.** Не спрашивать,
  не ждать, не помечать «нужно уточнение». Решение принимать на своё
  усмотрение — доверие полное.
- Спорные решения принимать самому, выбирая вариант, который сохраняет
  работающую игру и проверяемость.
- Если вариант необратим или уничтожает данные — выбрать обратимый.
- Если есть два пути, а критерия выбора нет — брать тот, который проще
  проверить запуском, и записывать выбор в `PROCESS.md` с обоснованием.
- Если не хватает ассетов — сгенерировать заглушку и пометить её.
- Если в ТЗ противоречие — выбрать вариант, сохраняющий работающую игру,
  записать противоречие в раздел блокеров.
- **Если задача блокирующая настолько, что без пользователя её решить нельзя**
  (нет доступа, нет файла, требуется его личное решение, нужны деньги или
  внешний аккаунт): не останавливаться. Пропустить шаг, пометить его `[-]` с
  причиной, **сразу записать его в раздел «Блокеры» в самом верху
  `PROCESS.md`** и перейти к следующей задаче.
- Останавливаться только когда: план выполнен, либо все оставшиеся пункты
  упираются в один и тот же непреодолимый блокер.
- Не отчитываться «в процессе» без результата: отчёт — по завершённым шагам.

### 7.1. Раздел «Блокеры» в PROCESS.md

- Живёт **первым** разделом файла, до «Снимка состояния».
- Пополняется сразу, как блокер найден, а не в конце работы.
- Формат строки: что нужно, почему нельзя решить самому, что сделано вместо
  этого (какой обходной путь выбран), какой пункт плана из-за этого пропущен.
- В итоговом отчёте пользователю блокеры идут первым блоком, до списка
  сделанного.

## 8. Что считается завершением

Работа считается выполненной, когда:

1. все пункты roadmap из `PROCESS.md` закрыты или явно помечены `[-]` с
   причиной;
2. `PROCESS.md` отражает реальность, у каждого закрытого пункта есть хеш
   коммита;
3. тесты зелёные, боты проходят, чистый прогон без ошибок;
4. игра запускается и играется;
5. раздел «Блокеры» в `PROCESS.md` актуален: в нём либо пусто, либо
   перечислено всё, что нельзя было решить без пользователя;
6. итоговый отчёт пользователю на русском: сначала блокеры, затем что
   сделано, что нет и почему.

## 9. Итоговый отчёт пользователю

Пишется по-русски, кратко и по делу:

- **сначала блокеры** — что не удалось решить без пользователя и что сделано
  вместо этого;
- что сделано (с доказательствами: команды и результаты);
- что не сделано и почему;
- что сломано или рискованно;
- как запустить и проверить.

Без «всё готово», если готово не всё.
